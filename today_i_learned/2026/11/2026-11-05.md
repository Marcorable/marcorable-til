# 2026-11-05

## 오늘의 기록

CCRecorder에서는 SwiftUI 표현 경계와 녹음 상태를 정리한 작업을 출시 준비 단계까지 연결하고, Firebase 관측성과 플랫폼별 이슈 관리 기준을 다듬었다. 기능 구현과 자동 검증이 끝난 작업도 실제 기기, 개인정보 공개 항목과 삭제 범위처럼 사람이 확인해야 할 조건은 별도로 남겼다.

ReciteScripts에서는 접근성 리뷰를 반영하고 스토어 스크린샷 자동화로 다음 작업을 이어 갔다. 동시에 오늘 작성된 Record를 다시 읽으며 SwiftUI 설계, 이미지·오디오 처리, 테스트, 프로젝트 생성과 AI 시대의 학습 태도까지 오래 남길 핵심으로 압축했다.

- Firebase 관측성 작업을 PR #117로 올리고 Debug·Release 빌드, Release archive, 단위 테스트 125개, Analytics DebugView 수신과 새 크래시 심볼화를 확인했다.
- CCRecorder v2.0.0 상위 작업 12개가 Linear로 이관된 것을 확인했다. 제품 방향은 Linear, 저장소별 구현 상세는 GitHub Issue로 관리하며 Localization 작업은 iOS #118에 남겼다.
- ReciteScripts Issue #31의 PR #72 리뷰를 반영해 접근성 semantics, 오류 문구와 Android 설정 이동을 보완했다. Flutter 테스트 98개와 Android 단위 테스트·CI를 통과했고 미해결 리뷰 스레드는 없다.
- CCRecorder Android의 녹음·재생 구조를 Controller, 플랫폼 Backend와 ForegroundService의 책임으로 나누어 정리했다.
- marcorable-kit을 프로젝트마다 복사하는 대신 사용자 Plugin 캐시에 설치해 정본의 소유권과 소비 프로젝트를 분리하는 배포 방향을 검토했다.
- 포트폴리오의 핵심 메시지를 모듈화, MVVM 정리, TCA·에이전트·문서화로 이어지는 성장 흐름으로 정리하고 GitHub 핀 저장소 3개에 한 줄 앱 소개를 추가했다.

- 워크보드의 Linear 프로젝트 분류와 Non-app 라벨 정리를 진행하고 있다.

## 배운 점

### 완료 기준은 코드 상태와 외부 확인을 분리해야 한다

- 테스트와 빌드, archive 통과는 코드와 산출물의 자동 검증 결과다. API Key 제한, 개인정보 고지, 실기기 마이크와 삭제 범위는 같은 결과로 대체할 수 없다.
- 데이터가 저장됐더라도 화면이 갱신되지 않으면 사용자는 데이터가 사라졌다고 느낀다. 저장 성공뿐 아니라 화면 사이 복귀와 재조회까지 하나의 사용자 흐름으로 검증해야 한다.
- Linear에는 제품 방향과 플랫폼 간 큰 작업을, GitHub에는 특정 저장소의 구현 상세를 남기면 의사결정과 코드 변경의 경계가 선명해진다.

### 플랫폼 기능은 규칙과 실행, 생명주기를 분리하면 이해하기 쉽다

- Android 오디오에서 Controller는 상태 전이와 명령 규칙, Backend는 MediaRecorder·Media3 실행, ForegroundService는 운영체제 생명주기를 담당한다.
- SwiftUI에서도 화면 전체 조정과 녹음 Effect를 분리하면 Root는 대화 정보와 dismiss에 집중하고 하위 Feature는 녹음 상태와 취소 책임을 독립적으로 검증할 수 있다.
- 자동화 도구를 선택할 때는 API·CLI로 처리 가능한 데이터 작업을 우선하고, 실제 화면 확인이나 API가 제공하지 않는 필드에만 GUI 제어를 사용한다.

## 기록에서 배운 점

### [MV → MVVM](https://green1229.tistory.com/267)

- `@EnvironmentObject`를 ViewModel에 전달하려고 상위 View가 중계 책임을 갖기 시작하면 SwiftUI의 데이터 흐름과 MVVM 경계가 오히려 복잡해질 수 있다.
- SwiftUI에서는 View 자체가 상태 표현을 맡는 MV 접근도 검토하고, 로직은 Protocol로 분리하거나 View를 작은 역할 단위로 나누는 방법을 함께 비교해야 한다.
- 아키텍처 이름보다 프로젝트 규모와 팀의 학습 단계, `@State`·`@Binding`·`@EnvironmentObject` 같은 Property Wrapper의 역할을 정확히 사용하는 것이 먼저다.

### [Localization](https://www.kodeco.com/27469286-swiftui-localization-tutorial-for-ios-getting-started)

- iOS 다국어 지원은 `.strings`와 SwiftUI Localization의 기본 흐름을 이해하는 것에서 시작한다.
- 번역 문자열이 많아지면 iOS `Localizable.strings`와 Android `strings.xml`을 스프레드시트에서 함께 관리해 플랫폼 간 누락을 줄일 수 있다.
- WWDC·공식 문서·실전 사례를 구분해 모으면 API 사용법과 팀 운영 방식을 함께 비교할 수 있다.

### [Core Image Programming Guide](https://developer.apple.com/library/archive/documentation/GraphicsImaging/Conceptual/CoreImaging/ci_intro/ci_intro.html)

- Core Image는 CPU·GPU 렌더링 경로의 세부 구현을 감추고 필터, 얼굴 특징 감지, 자동 보정과 커스텀 효과를 제공한다.
- `CIImage`는 완성된 픽셀 버퍼가 아니라 렌더링 레시피다. 여러 필터를 연결하면 중간 이미지를 반복 생성하지 않고 전체 체인을 하나의 작업으로 최적화할 수 있다.
- 합성·생성·축소·전환 필터를 조합하면 단순 효과를 넘어 분석과 피드백 기반 처리까지 같은 파이프라인에서 구성할 수 있다.

### [Testing for errors in Swift code](https://app.notion.com/p/40cd5c4871bd81b497bdde38782dcfd2)

- Swift Testing의 `#expect(throws:)`에는 기대하는 구체적 오류를 전달해 실패 조건을 명시할 수 있다.
- 오류가 발생하지 않아야 하는 경로는 `Never.self`와 비교하면 의도를 테스트 안에 직접 표현할 수 있다.

### [What’s new in the Photos picker](https://app.notion.com/p/40cd5c4871bd81ae89b2f895c1efbdfe)

- `PHPickerConfiguration`은 필터, 선택 순서와 최대 선택 개수를 선언적으로 구성한다.
- 사진과 영상은 다운로드나 변환 때문에 즉시 로드되지 않을 수 있으므로 인라인 로딩 상태를 제공해야 한다.
- SwiftUI의 `PhotosPicker`는 `Transferable`을 이용해 앱과 확장 사이의 데이터 전달을 타입 안전하게 구성할 수 있다.

### [토스 SLASH 22 — iOS 앱을 매주 배포한다고?](https://app.notion.com/p/40cd5c4871bd814cb1d3ff975a1df8d6)

- 대규모 앱은 코드량과 모듈·SDK가 늘면서 빌드와 개발환경 설정 자체가 생산성 문제로 바뀐다.
- 온보딩, 기능 개발, 내부 배포와 릴리즈 관리를 연결하고 Jenkins·Fastlane 같은 자동화로 반복 판단을 줄여야 주간 배포가 가능해진다.
- 자동화의 목표는 명령 수를 줄이는 것보다 릴리즈 담당자가 매번 해야 하는 고민을 줄이는 데 있다.

### [AVAudioEngine Tutorial for iOS](https://app.notion.com/p/40cd5c4871bd81ddac4ce22e7f8dcf9b)

- `AVAudioEngine`은 `AVAudioPlayerNode`, `AVAudioUnitTimePitch` 같은 노드를 연결해 오디오 처리 그래프를 만든다.
- 파일을 `AVAudioFile`로 열고 Player Node에 예약한 뒤 재생하며, Time Pitch 노드로 속도와 피치를 바꿀 수 있다.
- 오디오 탭의 `AVAudioPCMBuffer`로 VU Meter를 만들고 `AVAudioFramePosition`으로 재생 위치를 이동할 수 있다.

### [리액티브 스위프트 Combine](https://app.notion.com/p/40cd5c4871bd8137b521c2683e430dd9)

- Publisher는 값을 내보내고 Subscriber는 완료·실패와 값을 받는다. 실패하지 않는 스트림은 오류 타입을 `Never`로 표현한다.
- `sink`로 구독을 만들고 `AnyCancellable`을 보관·취소해 구독 생명주기를 관리한다.
- NotificationCenter, KVO와 API 호출도 Publisher로 바꾸면 debounce 검색이나 동시·연쇄 요청을 같은 데이터 흐름으로 다룰 수 있다.

### [Tuist](https://app.notion.com/p/40cd5c4871bd813e854cfd3a598a880f)

- Tuist의 목표는 프로젝트 파일 생성 자체가 아니라 Xcode의 복잡성을 Swift 선언과 검증 도구로 압축해 프로젝트를 유지하기 쉽게 만드는 것이다.
- SPM이 의존성 관리에 집중한다면 Tuist는 Project, Workspace, Target과 Scheme까지 정의하면서 SPM·CocoaPods·Carthage 의존성을 함께 연결한다.
- 마이그레이션은 빌드 설정을 `.xcconfig`로 추출하고 의존성이 적은 Target부터 옮기며, 누락 참조와 미사용 파일을 먼저 정리하는 편이 안전하다.
- 생성된 `.xcodeproj`를 직접 수정하지 못하도록 CI 검사를 두고 공통 패턴은 Project Description Helper로 추출한다.

### [Search](https://app.notion.com/p/40cd5c4871bd816da073da96f22985d6)

- `UISearchController`는 `UISearchResultsUpdating`을 통해 입력 변화에 반응하고, 별도 결과 ViewController 사용 여부에 따라 표시 구조를 선택할 수 있다.
- iOS 13의 `UISearchToken`은 위치나 범주처럼 텍스트보다 복잡한 검색 조건을 표현하며, `representedObject`에는 가벼운 값을 담는 편이 안전하다.
- 검색 결과 화면은 loading, error, empty, populated와 paging을 enum 상태로 모델링하면 서로 양립할 수 없는 UI 상태를 막을 수 있다.

### [Swift Master School — 진도 정리](https://www.inflearn.com/course/%EC%8A%A4%EC%9C%84%ED%94%84%ED%8A%B8-%EB%AC%B8%EB%B2%95-%EB%A7%88%EC%8A%A4%ED%84%B0-%EC%8A%A4%EC%BF%A8)

- 변수·타입·연산자와 제어 흐름에서 시작해 함수, Optional, Collection, Enum과 객체지향 문법으로 학습 범위를 단계적으로 확장했다.
- 클래스·구조체의 메모리 차이, 초기화와 상속, 타입 캐스팅, Extension, Protocol 지향 프로그래밍과 메서드 디스패치까지 이어지는 진도를 기록했다.
- 대부분의 강의는 완료했지만 일부 연습문제와 API 이해 강의는 미완료로 남아 있어, 진도율보다 비어 있는 기본기를 다시 확인하는 용도로 활용할 수 있다.

### [Camera](https://prod.velog.io/@horus222128/iPhone-Camera)

- PhotoKit의 영속 변경 토큰은 앱 실행이 끝난 뒤에도 사진 라이브러리 상태를 기억해 다음 실행에서 추가·삭제·수정 내역을 이어서 가져올 수 있다.
- 메모리 안의 Fetch Result 변화를 실시간으로 받는 `PHChange`와 장기간 변경 이력을 조회하는 API는 사용 목적이 다르므로 함께 사용할 수 있다.
- Asset, Asset Collection과 Collection List의 변경을 구분하면 매번 전체 라이브러리를 다시 불러오는 비용을 줄일 수 있다.

### [WWDC25 — Build a SwiftUI app with the new design](https://developer.apple.com/videos/play/wwdc2025/323/)

- Xcode 26과 표준 SwiftUI 구조를 사용하면 NavigationSplitView, TabView, Sheet, toolbar와 기본 control에 Liquid Glass가 대부분 자동 적용된다.
- 커스텀 배경, 불필요한 tint와 어둡게 처리하는 레이어가 시스템의 scroll edge·Glass 효과를 방해하는지 먼저 확인해야 한다.
- 가까운 커스텀 Glass 요소는 `GlassEffectContainer`로 묶고 `glassEffectID`를 연결하면 일관된 굴절과 morphing transition을 만들 수 있다.
- 앱 전체를 Glass로 꾸미기보다 표준 UI를 기반으로 두고 핵심 기능을 강조하는 요소에만 선택적으로 적용한다.
