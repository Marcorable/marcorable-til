# 2026-11-03

## 오늘의 기록

CCRecorder의 v1.3.0 정비를 이슈별 worktree로 병렬화하면서 구현, 리뷰, 병합과 작업 환경 정리를 하나의 흐름으로 다듬었다. 동시에 반복되는 판단을 marcorable-kit의 원자 규칙과 스킬로 옮겨, 특정 프로젝트의 구현 사례가 다른 Swift·Flutter·React Native 프로젝트에도 적용 가능한 작업 방식이 되도록 정리했다.

## 배운 점

### 원자 스킬은 한 방향의 상태 흐름만 책임져야 한다

- 부모가 소유한 상태를 Child에 넣는 입력 경로와 Child 결과를 부모에 병합하는 출력 경로는 서로 독립적으로 필요할 수 있다. 두 방향을 한 스킬이 항상 요구하면 읽기 전용이나 출력 전용 Child에 재사용하기 어렵다.
- Parent→Child 입력과 Child→Parent 출력을 각각 독립 스킬로 두고, 양방향 편집이 필요할 때만 얇은 workflow가 둘을 조합하면 책임과 적용 조건이 선명해진다.
- UI 표현인 '표시·편집 상태'보다 'Child 업무에 필요한 투영 상태'로 설명하면 UIKit, SwiftUI와 UI가 없는 업무 로직에도 같은 판단을 적용할 수 있다.

### 팩은 기술 환경과 작업 시점에 따라 선택되어야 한다

- Swift 공통 규칙, TCA 같은 아키텍처 규칙과 SwiftUI 같은 UI 프레임워크 규칙을 분리하면 UIKit 프로젝트에 불필요한 SwiftUI 지침을 넣지 않아도 된다.
- SwiftLint처럼 정적으로 검증할 수 있는 규칙은 문서만 반복하기보다 도구 설정으로 옮기는 편이 일관성을 높인다. 스킬은 SwiftLint 유무를 확인하고 필요한 설정을 추가하는 도입 절차에 집중할 수 있다.
- 프로젝트마다 필요한 팩 조합이 다르므로 전체 kit을 일괄 설치하기보다 현재 환경과 작업 범위에 맞는 팩만 선택하고 실제 생성물을 검증해야 한다.

### 완료는 구현, 자동 검증과 외부 상태를 구분해야 한다

- 테스트와 빌드 통과는 회귀와 컴파일 경계를 확인하지만 음성 입력, 접근성, Reduce Motion처럼 실제 기기와 사용자 설정에 의존하는 품질까지 증명하지는 않는다.
- stacked PR은 각 변경이 검증됐더라도 기반 PR이 병합되기 전에는 후속 브랜치의 최종 기준점이 확정되지 않는다. 코드 완료와 병합 가능 상태를 별도로 기록해야 한다.
- PR 병합 뒤 리모트 브랜치와 worktree를 정리하되 로컬 브랜치는 사용자가 직접 관리하도록 남기면 자동 정리와 복구 가능성의 경계를 유지할 수 있다.
