# 2026-11-18

## 배운 점

### Agentic Harness는 에이전트의 자율성을 통제 가능한 실행으로 바꾼다

- LLM은 추론을 담당하고 하네스는 도구 실행, 대화 상태, 권한, 승인과 안전 조치를 담당한다. Agentic Loop가 목표 달성까지 반복되는 과정이라면 Harness는 그 반복을 감싸고 관리하는 실행 환경이다.
- 개발자의 역할도 모든 코드를 직접 작성하는 데서 끝나지 않는다. 작업을 분해하고 에이전트에 배분하며, 스펙과 증거를 기준으로 결과를 승인하는 오케스트레이터 역할이 중요해진다.
- 하네스 문서는 서로 같은 상태를 복사하지 않아야 한다. 영구 규칙, 목표, 실행 절차, 현재 상태, 완료 증거의 진실 원천을 분리해야 시간이 지나도 시스템이 어긋나지 않는다.

### AI의 완료 보고와 테스트 통과는 검증의 시작점이다

- 테스트를 통과했다는 사실만으로 사용자가 요구한 동작이 완성됐다고 단정할 수 없다. 사람이 정의한 스펙과 실제 응답·화면·파일·로그 같은 실행 증거를 함께 확인해야 한다.
- 구현한 에이전트와 검증하는 주체를 분리하면 자기 결과를 낙관적으로 해석하는 문제를 줄일 수 있다. 코드를 작성하지 않은 에이전트나 사람이 원래 스펙만 보고 통과 여부를 판단하는 구조가 유효하다.
- 모바일에서는 권한 거부, 백그라운드 전환, 연결 중단과 취소 경쟁처럼 현실적인 실패 조건을 먼저 정의하고, 자원이 남지 않는지까지 관측해야 한다.

### iOS의 구조는 책임과 플랫폼 제약을 드러내야 한다

- MVC는 View와 Controller의 결합으로 ViewController가 비대해지고 독립 테스트가 어려워질 수 있다. MVVM은 ViewModel과 바인딩으로 View와 Model의 경계를 만들고, VIPER는 화면 표시·데이터 조작·화면 전환 책임을 더 세분화한다.
- 가장 좋은 아키텍처 패턴이 하나로 고정되는 것은 아니다. 패턴별 비용을 이해하고 앱 규모와 변경 이유에 맞게 책임을 분리하는 것이 중요하다.
- 커스텀 키보드는 `secureTextEntry`나 일부 Phone Pad에서 사용할 수 없고, 다음 키보드 전환 수단과 Host 앱이 필요하다. 입력 데이터와 가까운 확장인 만큼 사용자 신뢰와 데이터 보호를 기능보다 먼저 고려해야 한다.
- Open Access는 네트워크, 공유 컨테이너와 일부 사용자 데이터 접근을 가능하게 하지만 사용자가 직접 허용하는 권한이다. 필요한 기능과 수집 범위를 분명히 설명해야 한다.
- ZStack과 `overlay`의 차이와 선택 기준은 자료만 수집된 상태이므로 후속 학습에서 실제 레이아웃 크기와 정렬 동작을 비교할 필요가 있다.

### 작은 AI 제품도 먼저 유료 사용자를 정의해야 한다

- 기능을 빠르게 만드는 능력만으로 제품의 지속 가능성이 생기지는 않는다. 어떤 문제를 가진 사용자가 왜 비용을 지불할지를 먼저 정의해야 기능과 실험의 우선순위를 세울 수 있다.

## 기록에서 배운 점

### [Harness 1](https://www.anthropic.com/research/harness-design-long-running-apps)

- Agentic Harness는 모델을 감싸 도구, 대화 맥락, 권한과 안전 조치를 제공하는 실행 시스템이다.
- Agentic Loop는 정보 수집, 행동, 오류 처리와 검증을 목표 달성까지 반복하며 Harness는 이 과정을 통제한다.
- Codex와 Claude Code는 표현은 다르지만 모델과 실행 환경의 책임을 분리한다는 공통 구조를 갖는다.

### [AI가 “개발 완료”라고 하면, 어디까지 믿어도 될까?](https://yozm.wishket.com/magazine/detail/4039/)

- 테스트 통과만으로 완료를 선언하지 않는다.
- 실제 결과를 사람이 정한 스펙과 대조한다.
- 구현과 독립된 검증 주체가 통과 여부를 판단하도록 역할을 분리한다.

### [iOS 아키텍처 패턴: MVC, MVVM, VIPER](https://medium.com/ios-os-x-development/ios-architecture-patterns-ecba4c38de52)

- MVC는 View와 Controller를 분리하기 어렵고 ViewController가 커지기 쉽다.
- MVVM은 ViewModel과 바인딩을 통해 View와 Model 사이의 책임을 분리한다.
- VIPER는 Entity, Interactor, Presenter, View, Router로 데이터 조작, 표시 준비와 화면 전환을 세분화한다.
- 패턴 자체보다 각 책임의 경계를 이해하고 프로젝트에 맞게 적용하는 것이 중요하다.

### [Custom Keyboard Extensions: Getting Started](https://app.notion.com/p/40cd5c4871bd812bb1c3f8888d9f2fe3)

- 커스텀 키보드에는 다음 키보드로 전환하는 수단과 실제 목적을 제공하는 Host 앱이 필요하다.
- 보안 입력과 일부 전화번호 키보드에서는 확장을 사용할 수 없고 앱도 Extension 사용을 제한할 수 있다.
- `textDocumentProxy`로 입력과 삭제를 처리하고 `UILexicon`으로 제한적인 자동 교정 기능을 구현할 수 있다.
- Open Access가 필요한 기능은 사용자 신뢰와 데이터 보호를 전제로 설계해야 한다.

### [ZStack vs Overlay](https://app.notion.com/p/40cd5c4871bd81a8b950e8a2faa6d3b3)

- ZStack과 `overlay`의 차이 및 상황별 선택 기준을 확인하기 위한 참고 자료가 수집돼 있다.
- Record 본문에는 아직 비교 결론이 없어 후속 실험과 정리가 필요하다.

### [2인 팀이 AI로 만든 서비스, 유료 사용자 1600명까지](https://yozm.wishket.com/magazine/detail/4041/)

- 제품을 만들 때 기능 목록보다 비용을 지불할 사용자가 누구인지 먼저 고민해야 한다.
- Record에는 이 결론만 기록돼 있어 구체적인 성장 과정과 실행 전략은 원문을 다시 읽고 보강할 필요가 있다.

### [개발자에서 오케스트레이터로](https://helloworld.kurly.com/blog/ai-orchestration-1/)

- 개발자가 에이전트의 작업을 설계하고 조율하는 역할로 확장되는 관점을 참고하기 위해 수집한 글이다.
- Record 본문은 비어 있어 원문의 세부 내용은 이 TIL에서 추측하지 않았다.

### [팀 작업 흐름에 하네스 연결하기: UI 개발부터 검증 리뷰까지](https://yozm.wishket.com/magazine/detail/4040/)

- UI 개발부터 검증 리뷰까지 팀 작업 흐름에 하네스를 연결하는 사례를 참고하기 위해 수집한 글이다.
- Record 본문은 비어 있어 구체적인 구현 방식과 결론은 원문을 다시 읽은 뒤 보강해야 한다.
