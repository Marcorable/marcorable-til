# 2026-11-23

## 오늘의 기록

ReciteScripts의 생명주기 수정이 실제 기기에서도 의도대로 동작하는지 세 가지 시나리오로 확인하고, 결과를 이슈의 완료 근거로 남겼다. 상품상세 포트폴리오는 최신 문안을 2페이지 산출물로 렌더링해 레이아웃과 내용의 빈틈을 함께 점검했다. CCRecorder의 다음 릴리스와 Penpot 자산의 Figma 전환도 기능이나 도구를 바로 실행하기보다 범위, 검증 기준과 투자 기간을 먼저 정하는 관점으로 검토했다.

## 작업 기록

### 완료

- ReciteScripts에서 스크린샷 후 낭독 지속, 홈 화면 전환 시 세션 종료, 정상 완주 안내 1회 표시를 실제 기기에서 모두 확인했다.
- 기기·OS·커밋과 검증 결과를 Linear MAR-76에 기록하고 이슈를 Done으로 변경했다.
- 상품상세 재구축 포트폴리오의 최신 Notion 문안을 2페이지 A4 HTML·PDF로 렌더링하고 잘림과 겹침이 없음을 확인했다.
- 개인 README 프리뷰의 기술 배지를 아이콘 지원 여부에 따라 두 행으로 정리하고 Markdown 렌더러에 따른 이미지 배치 차이를 확인했다.
- Penpot 화면을 Figma로 옮길 때 핵심 화면만 Auto Layout, Component와 Variable 구조로 다시 만드는 단기 스프린트 방식을 검토했다.
- 매일 23:30에 Daily Log Memo와 당일 TIL 커밋을 확인해 빠진 작업만 보완하는 자동화 조건을 설정했다.

### 진행 중

- 상품상세 포트폴리오에는 5MD 분석에서 약 25MD 재구축 제안으로 이어진 판단 근거와 QA 범위, 탭 높이 전환의 한계를 보강해야 한다.
- CCRecorder v1.2.2는 핫픽스와 이후 기능 변경이 develop에 섞여 있어 출시 범위를 먼저 분리해야 한다.
- 기존 CCRecorder QA는 이전 커밋 기준이므로 버전 상승과 실기기 오디오·마이그레이션 시나리오를 최신 코드에서 다시 검증해야 한다.
- README 기술 배지의 최종 배치는 실제 GitHub 렌더링을 기준으로 한 번 더 확인해야 한다.

### 다음에 할 일

- 상품상세 포트폴리오에 일정 판단, 실기기 QA 범위, 재발 0건의 측정 범위와 구현 한계를 보강한다.
- CCRecorder v1.2.2의 순수 핫픽스 브랜치 범위를 확정하고 최신 커밋에서 출시 검증을 다시 수행한다.
- Penpot 대표 화면 하나를 Figma에서 재구축해 유료 기능과 에이전트 활용의 실제 효율을 먼저 시험한다.
- README 배지를 GitHub 렌더링에서 확인한 뒤 최종 형식을 결정한다.

## 배운 점

### 완료 조건은 실제 사용 환경의 서로 다른 경로로 검증한다

- 스크린샷 이후 세션 유지처럼 수정한 경로만 확인하면 반대편 회귀를 놓칠 수 있다. 홈 화면 전환에서는 종료되고 정상 완주에서는 안내가 한 번만 나타나는지 함께 검증해야 한다.
- 기기, OS, 커밋과 시나리오별 결과를 이슈에 남겨야 완료 판정이 개인의 기억이 아니라 다시 확인할 수 있는 증거가 된다.
- 코드 구현, 자동 테스트와 실기기 검증은 서로 대체되지 않는다. 플랫폼 생명주기처럼 환경 의존적인 동작은 마지막에 실제 기기 증거가 필요하다.

### 릴리스 범위가 달라지면 기존 QA 결과도 다시 해석해야 한다

- 핫픽스 외 변경이 develop에 함께 들어간 상태에서 브랜치 전체를 release로 보내면 의도한 버전 범위를 보장할 수 없다.
- QA 결과는 특정 커밋과 빌드에 대한 판정이다. 이후 변경이 포함되면 이전의 CONDITIONAL GO를 최신 릴리스의 근거로 그대로 사용할 수 없다.
- 버전 상승, 실제 마이크와 오디오 장치, 레거시 데이터 마이그레이션처럼 배포 환경에서만 확인 가능한 조건을 별도로 닫아야 한다.

### 포트폴리오는 레이아웃과 주장의 증거를 함께 검토한다

- 2페이지에 잘 들어간다는 사실만으로 제출 준비가 끝나지는 않는다. 여백이 크다면 문제의 복잡성, 대안 비교, QA 범위와 한계가 충분히 설명됐는지 확인해야 한다.
- `5MD 분석 → 약 25MD 재구축 제안`처럼 선택의 비용을 보여주는 수치와 `2주 이상 실기기 QA`, 재발 0건의 관찰 범위는 구현 목록보다 판단력을 잘 드러낸다.
- 결과 수치는 별도 트래킹 여부와 관찰 기간을 함께 밝혀야 과장 없이 신뢰를 줄 수 있다.

### 디자인 도구 전환은 화면 복사보다 설계 구조 재구축에 가깝다

- Penpot에서 SVG나 PNG로 옮기면 시각적 참고 자료는 보존할 수 있지만 Auto Layout, Component, Variable과 반응형 제약까지 자동으로 이어지지는 않는다.
- 전 화면을 기계적으로 변환하기보다 대표 화면을 다시 구성하며 토큰과 컴포넌트를 만드는 편이 이후 SwiftUI 구현과 포트폴리오 활용에 유리하다.
- 유료 도구는 장기 구독부터 시작하기보다 한 달짜리 목표와 평가 기준을 정하고 작은 화면으로 효율을 검증하는 방식이 안전하다.

### Markdown은 파일이 같아도 렌더러에 따라 표현이 달라질 수 있다

- Markdown 이미지와 HTML `img`의 인라인 배치는 GitHub, 에디터와 블록 기반 프리뷰가 서로 다르게 처리할 수 있다.
- 소스의 공백과 줄바꿈만 보고 최종 배치를 단정하지 말고 실제 게시 대상의 렌더러에서 확인해야 한다.
- 여러 환경에서 동일한 모양이 반드시 필요하다면 인라인 배지 여러 개보다 단일 SVG처럼 렌더링 단위를 줄이는 방법을 고려할 수 있다.
