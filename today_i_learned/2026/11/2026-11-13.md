# 2026-11-13

## 오늘의 기록

CCRecorder에서는 Necto 기반 진단 로깅을 전역 타입에서 공통 서비스 경계로 옮기고, 여러 모듈이 사용할 로거의 구성 방식을 검토했다. 말또는 App Store Guideline 2.1의 추가 정보 요청에 대응할 심사 노트와 운영 기록을 마련하고, GitHub Wiki 관리 방식을 재사용 가능한 스킬로 정리했다.

경력기술서는 프로젝트의 문제·해결·결과·기능 흐름과 실제 기간을 Git 이력에 맞춰 다듬었다. 학습 기록으로는 UICollectionView List, Combine, SwiftUI 레이아웃, FlexLayout과 HTTP·DNS·REST의 기초를 복습했다.

## 작업 기록

### 완료

- CCRecorder의 전역 `RecordingDiagnostics`를 Domain 계약과 `LoggerServiceConcrete.shared` actor 구조로 바꾸고, 녹음 이벤트를 구현체 내부 enum으로 관리했다.
- Necto 로깅을 기존과 동일하게 DEBUG에서만 활성화하고 시뮬레이터 Debug 빌드로 검증했다.
- 말또 App Review Notes에 실제 기기 영상 흐름, 앱 목적, 기능 접근 방법, 온디바이스 음성 인식과 개인정보 처리 내용을 정리했다.
- Guideline 2.1 대응용 Linear 하위 이슈 MAR-55를 만들고, GitHub Wiki를 Home과 Release Notes 중심의 간결한 구조로 정리했다.
- `maintain-github-wiki` 스킬을 marcorable-kit에 추가하고 공식 검증기, 동기화 테스트와 diff 검사를 통과했다.
- 경력기술서의 12개 프로젝트를 실제 Git 이력에 기반한 기간과 인과관계 중심 문장으로 정리하고, Notion과 A4 2페이지 PDF 프리뷰에 반영했다.
- 컬리 제출용 이력서·경력기술서와 자기소개서·포트폴리오 PDF를 각각 병합하고 페이지 순서, A4 크기와 잘림 여부를 확인했다.

### 진행 중

- marcorable-kit의 `maintain-github-wiki` 변경은 검증을 마쳤지만 아직 커밋·푸시하지 않았다.

### 다음에 할 일

- 말또의 실제 기기 사용 영상을 촬영하고 공개 링크 접근 권한을 확인한 뒤 App Review Notes와 함께 재심사에 제출한다.
- 공통 로거를 여러 모듈에서 사용할 필요가 커지면 Common의 정적 facade에 App Target이 시작 시 handler를 등록하는 구조로 확장한다.
- 고빈도 로그가 필요해지면 샘플링, throttling, batching과 bounded queue를 적용하고 SDK 저장·전송 비용을 측정한다.

## 배운 점

### 공통 로깅 API와 외부 SDK 구현을 분리한다

- 여러 모듈에서 사용하는 로거는 업무 도메인의 서비스라기보다 횡단 관심사에 가깝다. Common 모듈은 외부 SDK를 모르는 호출 API만 제공하고, App Target이 초기화 시점에 실제 handler를 등록하는 구조가 의존 방향을 깨뜨리지 않는다.
- 정적 facade와 closure 호출 비용은 낮다. 실제 성능 병목은 SDK의 이벤트 저장, listener 전달과 네트워크 전송에서 발생하므로 lock은 handler를 읽을 때만 짧게 사용하고 SDK 호출은 lock 밖에서 수행해야 한다.
- 사용자 행동이나 상태 전환 수준의 저빈도 로그는 부담이 작지만, 오디오 프레임이나 타이머처럼 고빈도 이벤트는 직접 모두 기록하지 말고 집계하거나 제한해야 한다.

### App Review 대응 기록과 사용자 릴리즈 노트를 분리한다

- App Review 대응 이슈에는 Apple의 요청, 확인한 제품 사실, 제출 체크리스트와 결과를 남긴다.
- GitHub Release Notes에는 심사 과정이 아니라 사용자가 체감하는 기능, 개인정보 보호 방식과 지원 환경만 기록하는 편이 역할에 맞다.
- 계정·결제·UGC가 없는 앱도 해당 사실을 명확히 쓰고, Apple의 기기 내 음성 인식 사용과 외부 서버로 데이터를 보내지 않는다는 점을 구분해 설명해야 한다.

## 기록에서 배운 점

### [iOS 14 Tutorial: UICollectionView List](https://app.notion.com/p/40cd5c4871bd8156a86dc73b4db2ed79)

- `UICollectionLayoutListConfiguration`을 사용하면 Compositional Layout의 세부 구조를 직접 구성하지 않고도 한 줄로 List 레이아웃을 만들 수 있다.
- `UICollectionView.CellRegistration`과 content configuration을 사용하면 셀의 표현을 셀 클래스 자체와 분리할 수 있다.
- Section Snapshot은 한 섹션의 계층형 데이터를 캡슐화하며, 섹션마다 서로 다른 레이아웃과 동작을 구성하는 데 유용하다.

### [성공과 실패를 결정하는 1%의 네트워크 원리](https://app.notion.com/p/40cd5c4871bd8192be71e25b612ec012)

- 브라우저는 URL을 해석해 HTTP 요청을 만들고, DNS resolver와 OS의 프로토콜 스택을 통해 서버의 IP 주소를 찾는다.
- 통신은 socket 생성, 상대 socket과의 연결, 데이터 송수신, 연결 종료 순서로 진행된다.
- IP 주소는 컴퓨터를, port는 그 컴퓨터 안의 통신 상대를 식별한다. 애플리케이션은 descriptor를 사용해 자신의 socket을 구분한다.

### [Rest API — 야곰캠프 3기](https://app.notion.com/p/40cd5c4871bd81a1a9a5fb108605c6eb)

- URL은 protocol, domain, path, query parameter와 fragment로 구성되며 HTTP와 HTTPS의 기본 port는 각각 80과 443이다.
- 요청에서는 method, header, query와 body의 역할을 구분하고, 응답에서는 2xx·4xx·5xx status code로 처리 결과를 표현한다.
- RESTful API는 자원 중심의 URI, 의미에 맞는 HTTP method와 status code를 사용하고 행위를 URL에 중복해 넣지 않는 것이 핵심이다.

### [Combine: Getting Started](https://app.notion.com/p/40cd5c4871bd81bdaf3cde9320c3cd4d)

- Publisher는 시간에 따라 `Output` 값이나 `Failure`를 내보내고, Operator는 upstream의 이벤트를 변환해 downstream으로 전달한다.
- Subscriber의 입력과 실패 타입은 연결된 Publisher의 `Output`과 `Failure`에 맞아야 한다.
- `AnyPublisher`로 구체 publisher 타입을 지우면 연산자 조합이나 구현 변경을 호출자에게 노출하지 않을 수 있다.

### [FlexLayout](https://zeddios.tistory.com/1251)

- FlexLayout은 flexbox 방식으로 레이아웃을 표현하며 UIStackView보다 다양한 API와 높은 성능을 목표로 한다.
- PinLayout과 함께 사용해 외부 위치와 크기를 정하고, 내부 자식 배치를 FlexLayout으로 구성하는 패턴을 살펴봤다.
- 성능 수치는 사용 조건에 따라 달라질 수 있으므로 실제 화면과 데이터 규모에서 별도로 측정해야 한다.

### [Properties, Layout, @ViewBuilder](https://singularis7.tistory.com/17?category=951840)

- SwiftUI View는 자주 다시 생성되는 값 타입이므로 영구 상태는 Model에 두고, 편집 모드나 애니메이션 끝점 같은 임시 상태에만 `@State`를 사용한다.
- 레이아웃은 컨테이너가 공간을 제안하고 자식이 크기를 선택한 다음 컨테이너가 위치를 정하는 순서로 진행된다. `layoutPriority`는 공간을 먼저 제안받을 View를 조절한다.
- `GeometryReader`는 제안받은 크기와 safe area 정보를 제공하고, `@ViewBuilder`는 여러 View 표현을 하나의 View 결과로 조합한다.
