# 2026-11-06

## 오늘의 기록

CCRecorder iOS v1.2.2 핫픽스 네 건을 병합하고 자동 테스트와 시뮬레이터 QA를 마쳤다. 코드 상태는 안정화됐지만 앱 버전 상향, 실기기 오디오와 레거시 마이그레이션 검증은 출시 조건으로 남겨 자동 검증과 실제 출시 가능 상태를 구분했다.

ReciteScripts 스토어 자동화와 접근성 개선을 이어 가는 한편, 포트폴리오 구조와 1페이지 경력기술서를 정리했다. Agent Harness Engineering 학습에서는 에이전트 성능을 모델 자체보다 컨텍스트·도구·권한·검증을 연결하는 실행 환경의 문제로 바라보고, 지침인 Guide와 기계적 검증인 Sensor의 균형을 점검했다.

## 작업 기록

## 배운 점

### 완료 조건은 자동 검증과 운영 검증을 분리해야 한다

- 테스트와 시뮬레이터 빌드가 통과해도 앱 버전, 실기기 하드웨어와 마이그레이션처럼 산출물 밖의 조건이 남아 있으면 출시 준비 완료로 볼 수 없다.
- `Conditional Go`처럼 충족된 조건과 남은 조건을 함께 기록하면 코드 병합과 출시 승인을 같은 의미로 오해하지 않게 된다.
- 작업 흐름 단위의 WIP 제한은 같은 핫픽스의 연속 PR을 하나의 목적 아래 묶으면서도, 서로 다른 제품 작업이 무제한으로 벌어지는 것을 막는다.

### 에이전트 품질은 지침보다 피드백 루프에서 강화된다

- Guide는 바람직한 행동을 설명하지만 Sensor는 Hook·테스트·리뷰처럼 결과를 관측하고 실패를 되돌려준다.
- 같은 실수가 반복되면 모델 탓으로 끝내지 않고 규칙이나 자동 검증으로 남기는 ratchet이 필요하다.
- 역할 이름도 활동명보다 책임을 드러내야 한다. 독립적으로 테스트·재현·보고하는 역할은 `QA`보다 `Tester`가 더 명확하다.

## 기록에서 배운 점

### [Point와 Pixel](https://developer.apple.com/library/archive/documentation/2DDrawing/Conceptual/DrawingPrintingiOS/GraphicsDrawingOverview/GraphicsDrawingOverview.html)

- Point는 iOS 레이아웃의 논리 단위이고 Pixel은 디스플레이의 실제 화소다. 기기 배율에 따라 한 Point가 여러 Pixel로 표현될 수 있다.
- SwiftUI의 크기와 위치는 `CGFloat`와 Point 기준으로 다루고, 이미지 자산이나 렌더링 결과를 확인할 때 Pixel 배율을 함께 고려한다.
- 텍스트의 실제 높이와 디자인 도구의 pt 표기는 같은 개념으로 단정하지 말고 폰트 메트릭과 시스템 레이아웃을 확인해야 한다.

### [Swift 개발자처럼 변수 이름 짓기](https://tv.naver.com/v/4980432/list/267189)

- 코드는 기계보다 사람이 읽기 위해 먼저 작성된다는 전제에서 이름이 동작과 실패 가능성을 설명해야 한다.
- 결과를 즉시 돌려주는 작업은 `fetch`, 사용자에게 요청하거나 실패할 수 있는 작업은 `request`로 구분할 수 있다.
- 작업 단위가 클로저나 Request 객체로 감싸져 있다면 `perform`이나 `execute`가 실행 책임을 더 잘 드러낸다.

### [Dynamic Dispatch와 성능 최적화](https://developer.apple.com/swift/blog/?id=27)

- Static Dispatch는 컴파일 시 호출 대상을 결정해 빠르지만 다형성 활용이 제한되고, Dynamic Dispatch는 런타임에 대상을 찾아 유연한 대신 비용이 든다.
- 오버라이드가 필요 없는 타입과 메서드에는 `final`, 파일 밖에서 보일 필요가 없는 구현에는 `private`를 사용해 컴파일러가 직접 호출로 최적화할 여지를 준다.
- Whole Module Optimization은 모듈 전체를 보며 `internal` 선언의 상속 가능성을 판단해 정적 디스패치를 늘릴 수 있다.

### [Monad란 무엇인가?](https://app.notion.com/p/40cd5c4871bd814a802edc7dde34ae66)

- Monad는 Functor의 `map` 변환 능력에 `flatMap`을 더하고 Monad 법칙을 만족하는 값 컨테이너다.
- 값이 없거나 미래에 준비될 값을 컨테이너 안에 둔 채 함수를 합성하면 중첩을 줄이고 비동기 non-blocking 파이프라인을 구성할 수 있다.
- Optional도 값을 매번 꺼내지 않고 내부 변환을 연결한다는 점에서 같은 사고방식을 보여 준다.

### [Swift String 효율적으로 쓰기](https://app.notion.com/p/40cd5c4871bd814fbfb6ed13429c6546)

- Swift `String`은 유니코드 `Character`의 Collection이라 Int 인덱스를 사용할 수 없고 `String.Index`로 접근해야 한다.
- 문자의 길이가 가변적이어서 `RandomAccessCollection`이 아니므로 먼 위치를 반복 탐색하면 기대보다 비용이 커질 수 있다.
- 알고리즘에서 반복적인 임의 접근이 필요하다면 한 번 `[Character]`로 변환하는 비용과 이후 접근 비용을 비교한다.

### [깊은 복사 VS 얕은 복사](https://www.freecodecamp.org/news/deep-copy-vs-shallow-copy-and-how-you-can-use-them-in-swift-c623833f5ad3/)

- 깊은 복사는 내부 데이터까지 독립된 메모리에 만들고, 얕은 복사는 같은 참조 주소를 공유한다.
- 값 타입 컨테이너라도 내부에 참조 타입이 있으면 전체가 자동으로 깊은 복사되는 것은 아니다.
- 참조 타입의 독립 복사가 필요하면 `NSCopying`, `Codable`·직렬화나 명시적 복사 초기화처럼 객체 그래프 전체를 다루는 전략이 필요하다.

### [google/promises를 활용한 Swift 비동기 프로그래밍과 에러 처리](https://github.com/google/promises)

- Promise는 completion handler가 중첩되는 문제를 체이닝으로 바꾸고 비동기 단계의 읽기 순서를 선형으로 만든다.
- 각 단계가 부수 효과를 줄인 함수를 반환하게 하면 성공 흐름을 조합하기 쉽고 에러 처리를 한곳으로 모을 수 있다.
- 단순히 문법을 줄이는 것보다 비동기 결과와 실패 전파 규칙을 명시하는 데 의미가 있다.

### [TDD](https://app.notion.com/p/40cd5c4871bd81b0b65deb3a484a6dbc)

- Red 단계에서 기대 동작을 실패로 확인하고, Green에서 테스트를 통과하는 최소 구현을 만든 뒤 Refactor에서 구조를 정리한다.
- 테스트가 요구사항과 설계의 청사진 역할을 하면 구현을 바꾼 뒤에도 행동이 유지되는지 빠르게 확인할 수 있다.
- 테스트 통과를 유지하면서 작은 단위로 리팩터링하는 흐름이 변경 비용을 낮춘다.

### [Swift로 다시 보는 객체지향 프로그래밍](https://soojin.ro/blog/solid-principles-in-swift)

- Massive ViewController는 한 타입이 화면 표현, 상태와 비즈니스 로직을 모두 맡는 SRP 위반 신호다.
- enum에 대한 `switch`가 여러 곳에서 반복되면 새 case마다 기존 코드를 수정하게 되므로, 프로토콜과 다형성으로 변경 지점을 모을 수 있는지 살펴본다.
- 하위 타입이 상위 타입의 기대 동작을 제한하면 LSP가 깨지고 상속 구조 자체의 의미도 약해진다.

### [Unit Testing Core Data in iOS](https://app.notion.com/p/40cd5c4871bd81e99ed3f0567afbbef3)

- 좋은 단위 테스트는 Fast, Isolated, Repeatable, Self-verifying, Timely라는 FIRST 특성을 지향한다.
- `NSInMemoryStoreType`을 사용하면 앱의 실제 SQLite 저장소를 오염시키지 않고 테스트마다 독립된 Core Data 환경을 구성할 수 있다.
- 비동기 Core Data 코드도 로그를 사람이 확인하는 대신 테스트가 성공과 실패를 스스로 판정하도록 만들어야 한다.

### [Fastlane](https://docs.fastlane.tools/getting-started/ios/setup/)

- CI는 변경을 지속적으로 통합하고 검증하는 과정이며, Continuous Delivery와 Deployment는 production 반영을 수동으로 승인하는지까지 자동화하는지에 차이가 있다.
- Fastlane의 `match`는 인증서와 프로비저닝 프로파일을 공유하고, `gym`은 빌드·서명, `deliver`는 메타데이터·스크린샷·앱 업로드를 맡는다.
- 릴리스 자동화의 핵심은 명령 수를 줄이는 데 그치지 않고 인증서, 산출물과 배포 절차를 재현 가능한 코드로 만드는 것이다.

### [Agent Harness Engineering](https://addyosmani.com/blog/agent-harness-engineering/)

- 코딩 에이전트는 **Model + Harness**다. 프롬프트, 도구, 컨텍스트 정책, Hook, 샌드박스, 서브에이전트와 피드백 루프가 실제 행동을 결정한다.
- 실패를 일회성 수정으로 끝내지 않고 AGENTS.md 규칙, Hook이나 테스트로 남기는 ratchet이 같은 사고의 반복을 줄인다.
- 파일시스템과 Git은 지속 상태, 샌드박스와 기본 CLI는 자기 검증 환경이 된다. 계획·생성·평가 역할을 분리하면 자기평가의 편향도 줄일 수 있다.
- context rot에는 오래된 맥락 압축, 긴 로그 외부화와 필요한 순간에만 지침을 여는 점진적 공개형 Skill이 효과적이다.
