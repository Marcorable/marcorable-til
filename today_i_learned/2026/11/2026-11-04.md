# 2026-11-04

## 오늘의 기록

CCRecorder에서는 Android 기반 구축부터 오디오·로컬 저장 계층까지 작업을 나누어 구현하고, iOS에서는 녹음 화면의 상태와 동작을 독립 TCA Feature로 분리했다. 자동 테스트와 빌드로 코드 경계를 확인한 뒤 실제 마이크, 백그라운드와 저장 실패처럼 기기 환경에 의존하는 항목은 후속 QA로 남겼다.

## 배운 점

### 기능 분리는 상태 소유권과 완료 신호를 함께 나눠야 한다

- 녹음 상태와 비동기 동작을 하위 Feature가 소유하게 하면 Root는 대화 정보 조립, Alert와 dismiss 같은 화면 수준 책임에 집중할 수 있다.
- Parent 입력과 Delegate 출력으로 경계를 만들면 하위 기능의 내부 상태를 노출하지 않고도 저장 완료나 취소 결과를 부모에 전달할 수 있다.
- 구조 분리의 완료 여부는 코드 이동보다 테스트, 빌드와 실제 사용 흐름이 같은 의미를 유지하는지로 판단해야 한다.

### 자동 검증과 실기기 검증은 서로 다른 실패를 찾는다

- 단위 테스트, 전체 테스트와 시뮬레이터 빌드는 상태 전이와 컴파일 경계를 빠르게 확인한다.
- 마이크 권한, foreground service, 백그라운드·잠금 화면과 파일 정리는 운영체제와 기기 환경의 영향을 받으므로 별도의 완료 조건이 필요하다.
- 자동 검증 통과와 출시 가능한 상태를 같은 의미로 기록하지 않으면 남은 위험과 다음 행동이 더 선명해진다.

### 공통 규칙은 정본과 적용 증거를 분리해야 한다

- 반복되는 규칙은 `marcorable-kit`을 공개 정본으로 두고, 앱 저장소에는 사용한 팩과 버전, 프로젝트별 예외와 실제 검증 사례를 남기는 편이 유지보수하기 쉽다.
- 전체 대화나 로컬 실행 상태보다 이슈, worktree, PR, 테스트와 사람이 내린 결정의 연결을 남겨야 에이전트 협업 과정이 포트폴리오의 증거가 된다.

## 기록에서 배운 점

### [Designing for iPhone Duo](https://developer.apple.com/design/human-interface-guidelines/designing-for-iphone-duo)

- 내부 카메라는 활성화되기 전까지 숨겨질 수 있으므로, 고정된 카메라 영역을 전제로 화면을 구성하지 않는다.
- 기기의 자세와 화면 비율 변화에는 기기 이름보다 size class와 동적 레이아웃을 기준으로 대응한다.
- 디스플레이의 각도와 형태가 달라져도 핵심 기능과 경험은 일관되게 유지해야 한다.
- toolbar, tab bar와 navigation control은 시스템이 제공하는 세로형 레이아웃을 따르고, 여러 자세에서 실제 앱을 빌드해 크기 변화를 확인한다.
