# 2026-11-20

## 오늘의 기록

개발자 포트폴리오를 기술 목록이 아니라 판단의 근거와 검증 결과를 보여주는 사례로 다시 구성했다. 동시에 출시 후 제품의 이슈와 다음 버전 범위를 점검하면서, 구현이 끝났다는 사실과 안전하게 배포할 수 있다는 판단은 서로 다르다는 점을 확인했다. 커리어 방향도 AI 도구 활용 자체보다 모바일 전문성을 바탕으로 문제 정의부터 출시와 운영까지 책임지는 Product Builder에 맞췄다.

## 작업 기록

### 완료

- 포트폴리오를 `문제 → 제약 → 대안 → 결정 → 구현 → 검증 → 한계` 흐름으로 설명하는 편집 원칙을 정리했다.
- 상품상세 재구축 사례를 이중 스크롤의 원인, 단일 스크롤 구조 선택, 동적 높이 보정과 검증 결과가 드러나는 2페이지 구성으로 압축했다.
- 모듈화·공통 ViewModel 사례에서 실제 적용 범위와 용어를 재검토하고, 동료의 채택을 구조 설계의 결과로 보여줄 근거를 정리했다.
- MVP·Firebase 운영 사례는 제출용 내용과 사실 확인용 작업 메모를 분리해 문서의 목적을 명확히 했다.
- CCRecorder의 다음 버전 범위와 ReciteScripts의 출시 후 이슈를 점검하고 우선순위를 정리했다.
- 프리랜서 준비를 위해 기존 제품 재구축·데이터 마이그레이션·출시 경험의 증거를 모았다.

### 진행 중

- CCRecorder 다음 버전은 핫픽스와 이후 기능 변경을 분리한 출시 범위 확정, 버전 상승과 실기기 QA가 남아 있다.
- ReciteScripts는 스크린샷 촬영 중 앱 상태 전환을 낭독 종료로 잘못 처리할 가능성이 있는 이슈를 최우선 후보로 정했지만 구현은 시작하지 않았다.
- 포트폴리오의 일부 적용 범위와 타입명, 팀 채택 수치는 실제 코드와 기록을 기준으로 한 번 더 확인해야 한다.

### 다음에 할 일

- 포트폴리오 각 사례의 주장마다 코드, QA, 운영 기록처럼 검증 가능한 증거를 연결한다.
- 다음 버전의 출시 범위를 별도 브랜치와 마일스톤 기준으로 확정하고 최신 코드에서 회귀 검증을 다시 수행한다.
- 앱 생명주기의 일시적인 비활성 상태와 실제 종료 상태를 구분하는 회귀 테스트를 먼저 설계한다.

## 배운 점

### 포트폴리오는 구현 목록보다 판단의 구조를 보여줘야 한다

- 기술 이름을 많이 나열하는 것보다 어떤 문제를 발견했고, 어떤 제약 속에서 대안을 비교했으며, 왜 현재 구조를 선택했는지를 연결해야 기술적 깊이가 드러난다.
- 결과는 단순한 구현 완료보다 QA 범위, 출시 후 재발 여부, 동료의 채택처럼 관찰 가능한 증거로 표현할수록 강해진다.
- 한계와 다시 한다면 바꿀 점을 함께 기록하면 선택을 스스로 검토할 수 있다는 신뢰를 줄 수 있다.

### 출시 준비는 코드 완료와 별개의 판단이다

- 개발 브랜치에 핫픽스와 다음 버전 변경이 섞여 있다면 테스트가 통과했어도 그대로 출시 범위로 사용할 수 없다.
- 기존 QA 결과는 검증 당시 커밋에 대한 증거다. 이후 변경이 추가됐다면 버전 상승, 빌드와 실기기 시나리오를 최신 기준으로 다시 확인해야 한다.
- 출시 후 오류는 사용자 증상만 보지 않고 앱 생명주기와 상태 전환처럼 플랫폼 이벤트까지 추적해야 우선순위와 수정 경계를 정확히 정할 수 있다.

### Product Builder는 책임 범위를 넓히는 역할이다

- AI를 빠르게 사용하는 능력만으로 Product Builder가 되는 것은 아니다. 문제를 정의하고 제품으로 만들며, 실제 결과를 검증하고 운영상의 다음 판단까지 책임져야 한다.
- 모바일 전문성을 버리는 대신 출시와 운영 경험을 기반으로 제품 전체에 대한 책임 범위를 넓히는 방향이 더 일관된 커리어 서사가 된다.
