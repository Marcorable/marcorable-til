# 2026-11-26

## 오늘의 기록

제품 아이디어와 개발 프로세스는 요구사항, 사용자 흐름과 화면 설계의 기준 원본을 분리하고 기능 ID로 연결하는 방향으로 구체화했다. ReciteScripts PR #135는 리뷰와 분석, 149개 테스트, 양 플랫폼 빌드를 통과한 뒤 병합했다. 포트폴리오 면접 준비는 제출물의 주장으로부터 꼬리질문을 역산해 모듈화, 동시성, 스크롤 구조, 캐시와 App Extension을 우선 학습 영역으로 좁혔다.

## 작업 기록

### 완료

- 단기 계획과 반복 루틴을 함께 관리하는 앱 아이디어의 초기 사용자를 본인으로 정하고 별도 기획 워크트리를 열었다.
- Manyfast는 기능 명세, FigJam은 사용자 흐름, Figma Design은 화면의 기준 원본으로 나누는 제품 설계 원칙을 정리했다.
- ReciteScripts PR #135의 리뷰·충돌·테스트·빌드를 확인하고 merge commit `7ba0bc6`으로 병합했다.
- 여러 저장소의 공통 템플릿은 조직 `.github`, 저장소별 차이는 각 저장소, PR 작성 절차는 Developer 스킬이 맡도록 책임을 구분했다.
- 최신 제출물 6개를 정본으로 삼는 면접 준비 워크트리와 포트폴리오 기반 iOS 학습 우선순위를 구성했다.
- Anthropic의 에이전트 설계 자료를 Agentic Loop, 대표 워크플로와 검증·도구 설계 원칙 중심으로 정리했다.

### 다음에 할 일

- 새 앱의 핵심 불편과 매일 사용할 최소 루틴 기록 흐름을 검증 가능한 MVP 가설로 좁힌다.
- 포트폴리오의 모듈화·동시성·이중 스크롤 사례부터 30초 설명, 대안, 트레이드오프와 한계를 답변으로 만든다.
- 제품 기능 ID를 Manyfast 명세, FigJam 흐름과 Figma 프레임에 실제로 적용해 추적성을 확인한다.

## 배운 점

### 제품 문서의 기준 원본은 책임별로 나눌 수 있다

- 요구사항과 비즈니스 규칙은 명세 도구, 행동 순서와 예외 분기는 FigJam, 시각적 상태와 컴포넌트는 Figma가 맡으면 같은 내용을 중복 작성하는 비용이 줄어든다.
- 세 도구가 분리되어도 같은 기능 ID를 사용하면 규칙 변경이 흐름과 화면에 반영됐는지 추적할 수 있다.
- 초기 사용자가 자신인 제품은 시장 전체를 추측하기보다 매일 실제로 사용하는지부터 검증하는 편이 빠르다.

### 면접 학습은 제출한 주장으로부터 역산한다

- 광범위한 질문 목록을 순서대로 외우기보다 포트폴리오의 문제, 선택, 제외한 대안, 검증, 한계에서 꼬리질문을 만든다.
- 구현 수치와 성과는 원자료로 방어 가능한 범위를 분리하고, 불명확한 OS 버전이나 관찰 기간은 확정 사실처럼 답하지 않아야 한다.
- 한 프로젝트를 30초 설명부터 근본 원인, 해결책, 대안, 본인 기여와 다시 할 때의 개선점까지 확장하면 기술 지식과 경험이 연결된다.

## 기록에서 배운 점

### [App Extension Programming Guide](https://developer.apple.com/library/archive/documentation/General/Conceptual/ExtensibilityPG/)

- App Extension은 컨테이너 앱과 별도로 실행되는 바이너리이며, 호스트 요청을 처리한 뒤 빠르게 종료되는 범위가 명확한 작업이다.
- 앱보다 낮은 메모리와 짧은 실행시간, 사용할 수 없는 API를 고려하고 App Group이나 공유 프레임워크로 필요한 데이터와 코드를 나눠야 한다.

### [Bring your app’s core features to users with App Intents](https://www.youtube.com/watch?v=REGJcedvheE)

- Intent는 동작, Entity는 대상, App Shortcut은 사용자가 실행하는 문장을 표현한다.
- 이 세 요소를 구성하면 앱 핵심 기능을 Shortcuts, Siri와 위젯 같은 시스템 표면으로 확장할 수 있다.

### [Explore enhancements to App Intents](https://app.notion.com/p/40cd5c4871bd813ead0bef51bf58f288)

- Entity 질의와 매개변수, 발견성을 함께 설계해야 사용자가 앱을 직접 열지 않고도 원하는 기능에 도달할 수 있다.
- 시스템 통합은 기능 노출만이 아니라 어떤 표현과 입력이 사용자의 의도를 안정적으로 식별하는지까지 포함한다.

### [Inspectors in SwiftUI: Discover the details](https://app.notion.com/p/40cd5c4871bd81c2ac52f7a4f3e59338)

- Inspector는 선택한 콘텐츠의 세부 정보와 편집 도구를 주 화면에서 분리해 제공한다.
- 같은 콘텐츠도 가용 공간과 플랫폼에 맞춰 사이드 패널이나 다른 표현으로 적응시켜야 한다.

### [Meet SwiftUI for spatial computing](https://app.notion.com/p/40cd5c4871bd8176b3e3d246ae651b63)

- visionOS에서는 window, volume과 immersive space를 목적에 따라 선택하고 깊이와 공간 배치를 인터페이스의 일부로 다룬다.
- 기존 SwiftUI 구조를 활용할 수 있지만 시선과 제스처 입력, 편안한 거리와 과도한 몰입을 함께 고려해야 한다.

### [Debug with structured logging](https://app.notion.com/p/40cd5c4871bd8185b6fcdefa3cd5fccc)

- Logger의 subsystem과 category, 로그 수준을 일관되게 나누면 장애 상황에서 필요한 기록을 검색하고 연결하기 쉬워진다.
- 개인정보는 privacy 옵션으로 보호하고 디버깅 가치와 런타임 비용을 함께 고려해야 한다.

### [Improve Core ML integration with async prediction](https://app.notion.com/p/40cd5c4871bd81a4ad4ef55b2c45c41f)

- 비동기 prediction은 호출 스레드를 점유하지 않고 모델 추론을 앱의 동시성 흐름에 통합하게 한다.
- 모델 로드와 예측의 실행 위치, 취소와 결과 반영 시점을 명확히 해야 UI 응답성과 상태 일관성을 함께 유지할 수 있다.

### [Discover Swift enhancements in the Vision framework](https://app.notion.com/p/40cd5c4871bd81f9b7d2e2a1788ec90f)

- Swift 친화적인 Vision API는 요청과 관찰 결과를 더 타입 안전하게 표현한다.
- async/await 흐름으로 비전 요청을 구성하면 콜백 중첩을 줄이고 오류와 취소를 구조적으로 처리할 수 있다.

### [Clean Swift (VIP)](https://app.notion.com/p/40cd5c4871bd81cd88d8df32ecf9a158)

- View, Interactor와 Presenter의 요청·응답·표시 흐름은 화면 표현, 비즈니스 로직과 데이터 변환의 책임을 나눈다.
- Router와 Worker까지 경계를 분명히 하면 테스트 대상을 좁힐 수 있지만 작은 화면에는 구조적 비용이 과할 수 있다.

### [TCA (The Composable Architecture)](https://app.notion.com/p/40cd5c4871bd81c084f1cc76ef3a44e1)

- State, Action, Reducer와 Store로 상태 변화를 명시하고 Effect로 비동기 작업을 모델링한다.
- 기능을 작은 reducer로 조합하고 action과 state 변화를 검증하면 복잡한 상태 흐름도 재현 가능한 테스트로 남길 수 있다.

### [Xcode의 Target, Project, Workspace 개념](https://app.notion.com/p/40cd5c4871bd81b9b367e8c5ddf488a0)

- Target은 빌드해서 만드는 산출물이고 Project는 파일 참조, 빌드 설정과 하나 이상의 Target을 보관한다.
- Workspace는 여러 Project와 Target의 관계를 한 작업 공간에서 관리하며 CocoaPods처럼 프로젝트가 추가되는 구성에서 필요하다.

### [Claude Code 101](https://app.notion.com/p/423d5c4871bd80699ff0fda259d276e3)

- 에이전트 도구 학습은 명령 사용법만이 아니라 컨텍스트 관리, 작은 반복, 결과 검증과 실패 복구를 함께 연습해야 한다.
- Agentic Loop를 이해하면 모델이 관찰, 판단, 도구 실행과 재검증을 반복하는 과정에서 사람이 책임질 지점을 구분할 수 있다.

### [Product Process](https://app.notion.com/p/424d5c4871bd805992caf2fd374bcd2c)

- 제품 개발은 문제와 사용자, 검증할 가설을 먼저 정한 뒤 요구사항, 흐름, 디자인, 구현과 검증으로 구체화한다.
- 각 단계의 산출물과 기준 원본을 분리하면 변경이 어디에서 시작되고 무엇을 함께 갱신해야 하는지 명확해진다.

### [애플은 찐 파괴왕: 30분만에 20개 스타트업을 보내다](https://app.notion.com/p/40cd5c4871bd81d7ac7debf18bd40cb9)

- Apple Pay Later, Tap to Pay, Freeform, Passkey와 WeatherKit처럼 플랫폼 기본 기능과 API는 별도 제품 시장을 빠르게 흡수할 수 있다.
- 플랫폼 위에서 제품을 만들 때는 현재 기능 차별화뿐 아니라 OS 제공 기능으로 대체될 가능성과 독립적인 가치를 함께 검토해야 한다.
