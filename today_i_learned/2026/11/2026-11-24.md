# 2026-11-24

## 오늘의 기록

Career HQ 포트폴리오의 사례별 문서 구조와 작성 원칙을 재사용 가능한 스킬로 정리하고, 다음 사례 초안에 적용했다. ReciteScripts 변경은 코드 리뷰를 통해 병합을 막을 문제가 없는지 점검했으며, GitHub 프로필 문서도 구성을 다듬어 게시했다. 구현이나 문서 작성 자체뿐 아니라 확인된 사실과 아직 검증하지 못한 범위를 분리해 남기는 데 초점을 맞췄다.

## 작업 기록

### 완료

- 포트폴리오 1·2에서 확정한 A4 구성과 작성 원칙을 `build-portfolio-case-study` 스킬에 반영하고 유효성 검사를 통과했다.
- 포트폴리오 3 초안에서 원더픽의 MVP 출시 경험과 베리모지의 Firebase 기반 운영 경험을 서로 다른 사례로 구분했다.
- 확인되지 않은 수익, 사용자, 전환율과 A/B 테스트 결과를 포트폴리오의 성과로 쓰지 않도록 범위를 정리했다.
- ReciteScripts의 STT 준비 상태, 세션 생명주기, 접근성과 큰 글씨 레이아웃 변경을 정적으로 검토해 P0/P1 문제를 찾지 못했다.
- GitHub 프로필 README 구성을 재정리한 커밋 `08100ff`를 `main`에 푸시하고 작업 트리가 깨끗한 상태임을 확인했다.

### 진행 중

- 포트폴리오 3의 두 번째 페이지는 서비스 고도화 시도를 측정·실험, 수익화, 리텐션의 세 축으로 묶는 방향을 검토 중이다.
- ReciteScripts 리뷰는 코드의 정적 검토까지 마쳤지만, 실행 권한 제한으로 `flutter analyze`와 테스트 결과는 확인하지 못했다.

### 다음에 할 일

- 포트폴리오 3에서 다섯 가지 운영 기능을 같은 비중으로 나열하지 않고, 세 가지 목적 아래 구현 범위와 검증 가능한 결과를 연결한다.
- ReciteScripts 변경은 `flutter analyze`와 테스트를 실행할 수 있는 환경에서 동적 검증을 보완한다.

## 배운 점

### 포트폴리오의 설득력은 기능 수보다 분류 기준에서 나온다

- Meta 광고 SDK, Firebase 이벤트와 A/B 테스트, 포인트·인앱결제, 오퍼월, 친구 초대, 다이어리를 같은 깊이로 나열하면 SDK 연동 목록처럼 보일 수 있다.
- 각 기능을 측정·실험, 수익화, 리텐션이라는 운영 목적 아래 묶으면 기술 규모가 크지 않아도 어떤 가설을 위해 무엇을 만들었는지 설명할 수 있다.
- 구현 이력은 Git으로 확인할 수 있지만 광고 성과, 실험 결과와 리텐션 효과는 별도 근거가 필요하다. 근거가 없을 때는 성과가 아니라 기반 구성이나 기능 시도로 표현해야 한다.

### 정적 리뷰의 결론에는 검증하지 못한 범위도 포함해야 한다

- STT 이벤트 순서와 세션 ID, generation, sequence 검사는 늦게 도착한 이벤트가 종료된 세션을 다시 바꾸지 않는지 판단하는 핵심 근거다.
- 접근성 라벨, 큰 글씨에서의 배치 전환과 관련 테스트가 있더라도 실제 분석과 테스트를 실행하지 못했다면 병합 가능성에 대한 정적 판단과 동적 검증 완료를 구분해야 한다.
- P0/P1 문제가 없다는 결론과 VoiceOver·TalkBack 자동 안내나 하드코딩 문구 같은 P2 개선점은 함께 기록할 수 있다.

### 재사용 가능한 작성 규칙은 다음 사례의 품질 기준이 된다

- 사례 문서는 `문제사항 정립 → 실행 및 진행 → 결과 → 역량과 회고` 흐름을 유지하고, 같은 대안 비교를 표와 별도 섹션에서 반복하지 않는 편이 명확하다.
- 최신 원문 전체를 대조하고 사용자가 수정한 표현을 되돌리지 않으며, 확인되지 않은 사업 성과를 만들지 않는 규칙을 스킬에 남기면 다음 포트폴리오에서도 같은 검증 기준을 재사용할 수 있다.
