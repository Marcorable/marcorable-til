## 배운 점

### 화면 상태는 표시 책임을 가진 한곳에서 소유한다

- 같은 실패 상태를 Root와 Child가 함께 보관하면 어느 값이 실제 화면을 결정하는지 모호해진다. Alert를 표시하는 Root가 `AlertState`를 소유하고 Child는 사건만 전달하면 Source of Truth가 선명해진다.
- 완료 여부처럼 다른 상태에서 계산할 수 있는 값은 별도로 저장하지 않는 편이 상태 불일치와 분기 수를 줄인다.
- 사용자 입력 반영과 debounce 저장을 하나의 Action 흐름으로 모으면 중복 helper 없이 상태 변경과 Effect의 수명을 함께 추적할 수 있다.

### 재사용 가능한 TCA 지침은 원자 판단과 조합 workflow를 나눈다

- Child 분리, Route의 Entity를 ID로 바꾸기, Navigation 소유권처럼 독립적으로 판단하고 검증할 수 있는 작업은 각각의 규칙과 스킬로 분리하는 편이 재사용하기 쉽다.
- 화면 전체 마이그레이션은 세부 규칙을 다시 설명하기보다 필요한 원자 작업을 순서대로 조합하는 얇은 workflow 역할에 집중할 수 있다.
- 반복 주입과 멱등성 검증은 문서가 읽기 좋은지를 넘어 실제 프로젝트에 안전하게 적용되는지를 확인하는 완료 조건이 된다.

### 여러 앱의 협업 체계는 정본과 역할 경계를 먼저 정해야 한다

- 앱마다 기존 작업 관리 도구가 다르면 하나로 강제 통합하기보다, 제품별 정본을 명시하고 개발·QA가 실행되는 GitHub 이슈와 연결하는 편이 현실적이다.
- Designer·Developer·QA·Marketer의 산출물과 Workspace Manager의 조정 책임을 분리하면 여러 앱을 동시에 운영하면서도 결정권과 실행권이 섞이는 문제를 줄일 수 있다.
