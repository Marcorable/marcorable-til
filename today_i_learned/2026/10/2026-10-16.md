# 2026-10-16

## 오늘의 기록

CCRecorder v1.2.0의 심사 제출을 준비하며 iPad 방향 설정으로 인한 App Store 검증 오류를 해결하고 릴리스 브랜치에 반영했다. 동시에 SwiftUI 대규모 앱 구조를 학습하고, 두 QMarket 저장소의 과거 커밋을 조사했으며, NHN ACE iOS 개발자 채용 지원과 포트폴리오 보완을 마쳤다.

## 작업 기록

### 완료

- CCRecorder의 `develop → release` 릴리스 PR #68 병합을 확인했다.
- App Store 검증 오류 `90474: Invalid bundle`의 원인이 iPad 지원 방향에서 `PortraitUpsideDown`이 누락된 설정임을 확인했다.
- 이슈 #69와 `hotfix/#69`에서 방향 설정을 수정하고, Release 빌드 및 Store Validation을 마친 뒤 PR #70을 `release`에 병합했다.
- 원격 hotfix 브랜치 삭제와 로컬 `release` 최신 동기화를 확인했다.
- `QMarket-iOS-develop`, `Qmarket-Partners-iOS-develop`의 커밋·브랜치·태그·diff에서 `QoQ` 관련 표기를 조사했으나 유의미한 이력은 찾지 못했다.
- NHN ACE iOS 개발자 채용에 지원하고, 포트폴리오에 AdMob·Firebase 경험을 보완했다.

### 다음에 할 일

- App Store Connect v1.2.0 제출 전 새 연령 등급 설문의 랜덤박스 항목을 갱신한다.
- iPad 스크린샷이 제출 버전에 연결되어 있는지 확인한다.
- CCRecorder의 릴리스 노트를 최종 검토한 뒤 심사를 제출한다.

## 기록에서 배운 점

### [MVVM Isn’t Enough: Structuring Large SwiftUI Applications](https://khatzie.medium.com/mvvm-isnt-enough-structuring-large-swiftui-applications-28999a9fabaa)

- MVVM은 UI와 프레젠테이션 로직을 나누는 출발점이며, 대규모 앱 전체의 구조를 결정하는 아키텍처 자체는 아니다.
- 기능 단위로 코드를 구성하고 공통 인프라는 `Core`로 분리하면 변경 범위와 의존성을 더 명확히 관리할 수 있다.
- View는 UI 렌더링, ViewModel은 화면 상태, Use Case는 비즈니스 규칙, Repository는 데이터 접근을 맡기면 각 계층의 책임이 선명해진다.
- 프로토콜과 의존성 주입을 적용하면 구현 교체와 Mock 기반 테스트가 쉬워진다.
- Router/Coordinator, Repository, Use Case 같은 경계는 처음부터 모두 만들기보다 실제 복잡성이 생기는 지점에서 추가해야 한다.
