# 2026-W43 · 10월 19일 ~ 25일

> 이 요약은 해당 주간에 작성된 10월 19일~24일 일일 TIL을 기준으로 한다. 10월 25일 일일 기록은 없다.

## 이번 주 한 줄

CCRecorder의 화면 구조를 MVVM에서 TCA 중심으로 전환하고, 재사용 가능한 에이전트 규칙과 기록 자동화를 정비하는 한편 ReciteScripts의 Flutter MVP 요구사항을 실제 구현 가능한 수준으로 구체화했다.

## 완료한 일

### CCRecorder 아키텍처 전환

- 화면 구조와 명명을 정리한 뒤 RecordScreen의 상태, 비동기 Effect, Usecase 의존성과 저장 정책을 TCA Feature로 옮겼다.
- 권한 대기와 화면 종료 사이의 취소 경합을 점검하고 TestStore로 생명주기와 저장 정책을 검증한 PR #93을 병합했다.
- 노트 목록의 선택·삭제·sheet presentation 상태를 Feature가 소유하도록 전환하고, 재사용 목록 View를 `NoteBoard`로 정리했다.
- v2.0.0의 적응형 UI, CloudKit·파일 동기화, 멀티윈도우와 접근성 범위를 이슈 #79~#90으로 나눴다.
- 재생 시간 형식을 `PlaybackTimeFormatStyle`로 통합하고 SwiftData·FocusState 환경을 포함한 프리뷰를 보강했다.

### 공통 개발 규칙과 자동화

- `marcorable-kit`의 공통 정본과 에이전트별 생성물을 분리하고 Claude·Codex 동기화 흐름의 멱등성과 YAML 처리를 보완했다.
- Swift와 SwiftUI 규칙의 역할을 나누고 `marcorable-tca`, GitHub, Orca 팩을 추가·보강했다.
- MVVM과 TCA 팩의 동시 주입을 막고, 실제 CCRecorder 구현에서 확인한 Feature·presentation·의존성 규칙을 공통 문서로 환류했다.
- 세션을 Notion Daily Log Memo로 모으는 `daily-log-session-summary` 스킬을 만들고 누락된 일일·주간 기록을 보완했다.
- `marcorable-workspace`에 작업 우선순위, WIP 제한, 승인 경계와 에이전트 자율 운영 흐름을 문서화했다.

### ReciteScripts와 제품 준비

- ReciteScripts에 공통 작업 규칙과 Flutter 양 플랫폼 검증 환경을 적용하고 기술 전환 회고를 반영했다.
- MVP의 STT 중단, 늦은 결과 폐기, 플랫폼 이벤트 정규화와 Android 검증 기준을 요구사항에 추가했다.
- Flutter MVP PRD와 요구사항 추적표를 만들고, 화면을 목록·대본 추가·낭독 세 라우트로 제한해 오류와 이탈 흐름까지 정의했다.
- ReturnTheFavor의 핵심 가설과 8주 React Native 학습 로드맵을 정리하고, 구현 전 SQLite·알림·연락처 기능을 독립적으로 검증하기로 했다.

### 릴리스와 작업 추적

- `marcorable-mvvm`의 UIKit·SwiftUI 화면 전환을 `Navigator<Screen>`으로 통일하고 빌드·테스트 후 v0.2.0을 배포했다.
- CCRecorder의 구조 변경을 이슈와 PR에 연결하고, ReciteScripts의 요구사항 문서도 PR 리뷰와 병합 상태까지 추적했다.

## 학습과 판단

### 상태 소유권과 비동기 생명주기

- 화면 전환 명령과 렌더링 책임을 분리하면 UIKit과 SwiftUI가 같은 내비게이션 API를 공유할 수 있지만, 환경 주입과 구독 소유권도 함께 검증해야 한다.
- TCA 전환은 타입을 Feature로 감싸는 작업이 아니라 상태의 소유자, Effect 취소 시점, 저장 실패 정책과 presentation 경계를 명확히 하는 과정이다.
- 권한 요청처럼 응답이 늦을 수 있는 작업은 화면 이탈 후 결과가 도착하는 경우까지 테스트해야 파일 생성이나 상태 갱신 경합을 막을 수 있다.

### 적응형 UI와 데이터 동기화

- 적응형 레이아웃은 기기 이름보다 크기 등급, Dynamic Type, 현지화, 창 크기와 안전 영역의 변화에 대응해야 한다.
- SwiftData의 기기 간 동기화는 CloudKit capability와 호환 가능한 모델 스키마가 필요하며, 기존 CloudKit 구성과의 충돌도 먼저 확인해야 한다.

### 규칙과 지식의 유지보수

- 여러 에이전트의 규칙은 공통 정본에서 생성하고 실제 프로젝트에서 반복 검증해야 내용의 분기와 자동 생성 오류를 줄일 수 있다.
- 오래된 메모리는 현재 Git·PR·Issue 상태와 대조하고, 백업과 Archive를 남긴 뒤 수정해야 잘못된 맥락의 재사용을 막을 수 있다.
- 학습 기록은 공식 문서 읽기에서 끝내지 않고 최소 재현, 프로젝트 적용, 검증 결과와 설명 가능한 판단 근거까지 이어져야 한다.

## 다음 주 우선순위

1. CCRecorder의 화면 전환을 TCA Navigation으로 옮기고 기존 MVVM 의존성을 제거하기 전에 빌드와 회귀 테스트를 완료한다.
2. 노트 목록 presentation 상태의 Sendable 경고를 명시적 dismiss Action 또는 `persistentModelID` 방식 중 하나로 안전하게 해소한다.
3. ReciteScripts 핵심 사용자 흐름 문서의 리뷰를 반영하고 Android STT 스파이크 결과를 PRD의 출시 수용 기준에 연결한다.
4. 최신 `marcorable-kit` 규칙을 CCRecorder에 동기화하고 Swift·SwiftUI·TCA 팩의 실제 적용 결과를 다시 공통 규칙에 반영한다.
5. ReturnTheFavor의 대표 사례와 문제 정의를 보강하고 React Native 로드맵의 JavaScript 기초 학습을 시작한다.
