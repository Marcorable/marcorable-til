# 2026-W47 · 11월 16일 ~ 22일

> 이 요약은 이번 주에 작성된 11월 16일·17일·18일·20일·21일 일일 TIL을 기준으로 한다. 11월 19일·22일 일일 기록은 아직 없다.

## 이번 주 한 줄

모바일 제품의 로깅·현지화·생명주기 문제를 테스트와 빌드, CI 증거로 검증하고, AI 하네스와 포트폴리오에서도 구현 자체보다 완료 조건과 책임 범위를 명확히 하는 방향을 정립했다.

## 완료한 일

### CCRecorder 진단과 현지화

- Necto 기반 녹음 진단 이벤트를 ServiceConcrete와 UsecaseConcrete 경계에 적용하고 Domain 26개 테스트, 앱 테스트와 시뮬레이터 빌드로 검증한 PR #131을 병합했다.
- Localization 변경을 앱 타깃 설정과 Presentation 문자열 적용으로 분리해 PR #132로 구성했다.
- Tuist generate, Simulator Debug 빌드, CI-Unit 테스트와 String Catalog 검사를 통과했다.
- 리뷰에서 발견한 단어 입력 prompt와 녹음 화면의 사용자·VoiceOver 문구 회귀를 수정하고 검증을 다시 수행했다.
- 다음 버전의 핫픽스와 이후 기능 변경이 섞인 상태를 확인하고, 출시 범위와 기존 QA 증거를 최신 코드 기준으로 다시 검토해야 한다는 결론을 내렸다.

### ReciteScripts 출시 후 오류 수정

- 스크린샷 촬영으로 발생하는 일시적인 `inactive` 상태와 실제 백그라운드 전환·화면 종료를 구분하도록 생명주기 처리를 수정했다.
- 유지돼야 하는 세션과 정리돼야 하는 세션을 검증하는 회귀 테스트 2개를 추가했다.
- 전체 140개 테스트, Android·iOS 빌드와 GitHub CI를 통과하고 변경을 PR #128로 정리했다.
- 기존 PR #122·#124도 자동 검증을 통과했으며 최종 리뷰와 병합만 남겼다.

### AI 하네스와 지식 관리

- Agentic Harness를 모델의 반복 실행에 도구, 맥락, 권한, 승인과 안전장치를 연결하는 실행 체계로 정리했다.
- 영구 규칙, 목표, 반복 절차, 현재 상태와 완료 증거가 서로 다른 문서를 진실 원천으로 갖는 세컨 브레인 구조를 검토했다.
- 첫 모바일 하네스 실험 후보로 녹음 취소 후 임시 파일과 실행 세션이 남지 않는 실패 조건을 정의했다.
- 구현 주체와 검증 주체를 분리하고, 테스트 결과뿐 아니라 화면·파일·로그 같은 실제 증거를 완료 판단에 사용해야 한다는 원칙을 정리했다.

### 포트폴리오와 지원 준비

- 메리츠증권 지원서를 제출하고 iOS, 금융 실시간 데이터와 운영 안정성을 중심으로 면접 질문을 정리했다.
- 컬리 제출 자료의 상품상세 재구축, 모듈화, MVVM·Concurrency와 AI 협업 경험에서 검증될 가능성이 높은 질문과 사실관계 체크포인트를 Record로 남겼다.
- 포트폴리오 사례를 `문제 → 제약 → 대안 → 결정 → 구현 → 검증 → 한계` 구조로 편집하는 원칙을 세웠다.
- 상품상세 재구축, 모듈화·공통 ViewModel, MVP·Firebase 운영 사례를 판단 근거와 검증 결과가 드러나도록 재구성했다.
- 커리어 방향을 AI 도구 사용 자체가 아니라 모바일 전문성을 기반으로 문제 정의부터 출시와 운영까지 책임지는 Product Builder로 정리했다.

### 제한된 외주 실험 설계

- 국내 외주 채널 조사를 마치고 초기 채널을 위시켓과 크몽으로 좁혔다.
- 취업 준비를 우선하기 위해 운영 시간을 주 2시간으로 제한했다.
- 첫 4주 목표를 위시켓 맞춤 지원 6건과 크몽 서비스 2개 공개로 정하고, 직접 수주는 계약·견적 템플릿을 완성한 뒤 시작하기로 했다.

## 학습과 판단

### 완료 보고는 증거와 배포 경계로 검증한다

- 테스트 통과는 완료 판단의 일부일 뿐이다. 요구한 동작이 실제 응답, 화면, 파일과 로그에 나타나는지 원래 스펙과 대조해야 한다.
- 기존 QA 결과는 검증 당시 커밋에 대한 증거다. 이후 코드나 출시 범위가 바뀌면 최신 기준에서 빌드와 실기기 시나리오를 다시 검증해야 한다.
- 구현, PR 작성, 자동 검증, 병합과 배포는 서로 다른 완료 단계다. 각 단계의 상태를 분리해야 남은 위험을 정확히 설명할 수 있다.

### 모바일 상태는 이름보다 전환의 의미가 중요하다

- `inactive` 같은 플랫폼 상태는 항상 사용자 작업의 중단을 의미하지 않는다. 스크린샷처럼 세션을 유지해야 하는 이벤트와 실제 백그라운드·종료를 구분해야 한다.
- 오류를 고칠 때는 문제 경로만 확인하지 않고, 유지 조건과 정리 조건을 각각 테스트로 고정해야 반대 방향의 회귀를 막을 수 있다.
- 진단 이벤트도 시작·완료·실패를 일관되게 남기고 서비스와 유스케이스, 화면 경계까지 검증해야 운영 중 원인을 추적할 수 있다.

### 현지화와 접근성 문구는 사용자 동작의 일부다

- String Catalog의 개발 언어와 fallback을 명시하지 않으면 번역이 없는 환경에서 key가 그대로 노출될 수 있다.
- prompt와 VoiceOver title은 코드상의 문자열이 아니라 사용자 행동을 안내하는 인터페이스이므로 기존 의미와 함께 회귀 검증해야 한다.
- 프로젝트 설정과 화면 문자열 적용을 커밋 경계로 나누면 기반 변경과 사용자 경험 변경을 독립적으로 검토할 수 있다.

### AI 하네스는 자율성을 검증 가능한 실행으로 바꾼다

- LLM이 추론을 담당한다면 하네스는 도구, 상태, 권한, 승인과 안전장치를 관리한다. 반복 실행을 맡기는 것보다 완료 조건과 중단 조건을 설계하는 일이 중요하다.
- 구현 에이전트와 독립된 검증 주체가 원래 스펙만 보고 결과를 판단하면 자기 결과를 낙관적으로 해석할 위험을 줄일 수 있다.
- 영구 규칙, 목표, 실행 절차, 현재 상태와 완료 증거는 같은 내용을 복제하지 않고 각자의 진실 원천을 가져야 한다.

### 포트폴리오와 면접은 판단의 구조를 보여준다

- 기술 목록보다 어떤 문제와 제약이 있었고, 대안을 어떻게 비교했으며, 무엇으로 결과를 검증했는지를 연결해야 기술적 깊이가 드러난다.
- 수치는 측정 조건과 범위를 함께 밝히고 개인 기여와 팀 성과를 구분해야 한다.
- AI 협업은 완전 자동화로 포장하기보다 입력, 권한, 산출물, 완료 조건과 사람의 승인 지점을 설명하는 편이 신뢰를 높인다.
- Product Builder는 모바일 전문성을 버리는 역할이 아니라, 이를 기반으로 문제 정의와 출시·운영까지 책임 범위를 넓히는 역할이다.

### 새로운 수익 활동은 제한된 실험으로 시작한다

- 초기 채널과 실행 기간, 행동 목표를 좁히면 무엇이 효과적인지 비교하기 쉬워진다.
- 주간 시간 상한을 먼저 정하면 외주 탐색이 취업 준비라는 우선순위를 침범하는 것을 막을 수 있다.
- 직접 수주는 계약과 견적 기준을 준비한 뒤 시작해야 범위와 비용에 대한 운영 위험을 줄일 수 있다.
