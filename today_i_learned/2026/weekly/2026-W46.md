# 2026-W46 · 11월 9일 ~ 15일

> 이 요약은 이번 주에 작성된 11월 9일·10일·11일·13일·15일 일일 TIL을 기준으로 한다. 11월 12일·14일 일일 기록은 아직 없다.

## 이번 주 한 줄

ReciteScripts를 접근성 검증과 비공개 Alpha 배포까지 진전시키고, CCRecorder의 관측성·공통 로깅 경계를 정비했으며, App Review 대응과 경력기술서까지 제품 출시와 커리어 산출물을 함께 구체화했다.

## 완료한 일

### ReciteScripts 디자인·접근성·출시 준비

- Penpot에 대본 목록, 추가, 낭독 설정·진행·완료·오류와 접근성 화면을 정리하고 마이크 권한 확인부터 반복 횟수 선택, 낭독 화면 진입으로 이어지는 Wireflow를 확정했다.
- 텍스트 선택 하이라이트와 I-beam을 활용한 앱 아이콘을 iOS 15개 규격과 Android 5개 density로 생성하고, 정적 분석과 테스트 102개를 통과한 PR #75를 병합했다.
- 권한·설정 흐름, 작은 화면과 긴 제목, Accessibility XL, Android 48dp 터치 영역, 비활성 버튼의 형태 단서와 유리 표면 대비를 여러 PR로 분리해 검증했다.
- PR #78·#80·#84·#85를 필수 CI와 리뷰 후 병합했다. PR #77은 검증과 리뷰 대응을 마쳤지만 최종 병합 여부가 남았다.
- QA 체크리스트 PR #111을 병합하고 접근성 골든 이미지 8장과 전체 134개 테스트를 준비했다.
- Android CD 빌드 `101172`을 Google Play 비공개 Alpha에 게시했다. 테스터 참여 링크 전달과 후속 실기기 확인은 남아 있다.
- 비활성 아이콘 겹침 수정 PR #124에서 분석, 위젯 테스트 19개, 골든 테스트 2개와 정책 검사를 통과했다.
- 스토어 프로모션 스크린샷과 iOS 심사 문서를 교차 검토하고 Figma 디자인 파일과 디자인 시스템 정리를 진행했다.

### 말또 App Review 대응과 운영 지식

- App Store Guideline 2.1의 추가 정보 요청에 맞춰 실제 기기 사용 영상 흐름, 앱 목적과 대상 사용자, 기능 접근 방법, 온디바이스 음성 인식과 개인정보 처리 내용을 포함한 App Review Notes 초안을 작성했다.
- 대응 작업을 Linear 하위 이슈 MAR-55로 만들고, GitHub Wiki를 Home과 Release Notes 중심의 간결한 구조로 정리했다.
- Wiki의 버전 기록을 별도 페이지 대신 한 페이지 안의 접힌 토글로 관리하고, 심사 대응 과정과 사용자 릴리즈 노트의 역할을 분리했다.
- 같은 관리 방식을 재사용할 수 있도록 marcorable-kit에 `maintain-github-wiki` 스킬을 추가하고 공식 검증기, 동기화 테스트와 diff 검사를 통과했다.

### CCRecorder 관측성과 서비스 경계

- Firebase App Check의 App Attest를 등록하고 CI용 debug token을 Xcode Cloud secret으로 구성했다. 관련 PR #130을 `develop`에 병합하고 Issue #129와 작업용 worktree를 정리했다.
- Necto 기반 전역 `RecordingDiagnostics`를 Domain 계약과 `LoggerServiceConcrete.shared` actor 구조로 옮기고, 녹음 이벤트를 구현체 내부 enum으로 관리했다.
- Necto 로깅은 기존처럼 DEBUG에서만 활성화하고 시뮬레이터 Debug 빌드로 검증했다.
- 여러 모듈에서 쓸 로거는 Common의 정적 facade에 App Target이 시작 시 handler를 등록하는 구조로 확장할 수 있도록 방향을 정리했다.
- App Intents·Quick Actions·App Actions·App Shortcuts를 자동 녹음이 아닌 하나의 `녹음 화면 열기` 라우트로 연결하는 플랫폼 공통 사용자 동작을 정의했다.

## 학습과 판단

### 접근성은 모양·실제 크기·환경 조합으로 검증한다

- 비활성 상태를 색상만으로 표현하면 대비와 색각 조건에서 의미가 사라질 수 있다. 금지 표시처럼 형태 단서를 함께 사용해야 한다.
- 선언된 버튼 크기가 충분해도 Navigation Bar 같은 상위 제약 때문에 실제 터치 영역은 줄어들 수 있으므로 플랫폼 렌더링 결과를 직접 측정해야 한다.
- 작은 화면, 긴 제목, 큰 글자 크기와 기본 배율을 함께 검증해야 한 접근성 수정이 다른 레이아웃 회귀를 만들지 않았는지 확인할 수 있다.

### 외부 도구 상태와 필수 품질 기준을 분리한다

- CodeRabbit rate limit은 코드 품질 실패가 아니라 외부 서비스 제한이므로 무한 재시도하거나 유일한 병합 차단 조건으로 삼지 않는다.
- 현재 PR head SHA를 대상으로 한 필수 CI와 Codex 리뷰를 확인하고, 이전 SHA의 검증 결과를 최신 변경의 증거로 사용하지 않는다.
- 구현, 테스트 통과, PR 병합, 스토어 배포와 실기기 검증은 서로 다른 완료 단계이므로 진행 상태를 분리해서 기록해야 한다.

### 공통 로깅은 호출 API와 SDK 구현을 분리한다

- 여러 모듈에서 사용하는 로거는 Domain 업무 계약보다 공통 인프라에 가깝다. Common은 외부 SDK를 모르는 API를 제공하고 App Target이 초기화 시 실제 handler를 등록하는 구조가 자연스럽다.
- 정적 facade와 closure 호출보다 SDK의 저장·전송 비용이 더 크다. lock은 handler를 읽을 때만 짧게 사용하고 SDK 호출은 lock 밖에서 수행해야 한다.
- 오디오 프레임처럼 고빈도 이벤트를 수집한다면 샘플링, throttling, batching과 bounded queue로 호출량을 제한해야 한다.

### Swift의 타입·비동기·UI 시스템은 소유권과 흐름으로 이해한다

- struct 안에 class 참조가 있으면 struct를 복사해도 참조 대상은 공유된다. 독립 상태가 필요하면 깊은 복사나 Copy-on-Write를 명시적으로 설계해야 한다.
- 함수 이후까지 저장되는 closure는 `@escaping`이 필요하고, 강한 참조 캡처와 순환 참조를 함께 고려해야 한다.
- Swift Testing과 `Result` 테스트는 정상·실패 경로를 모두 표현하고, `AsyncSequence`는 값의 비동기 흐름과 종료·취소를 하나의 반복 모델로 다룬다.
- Combine도 Publisher→Operator→Subscriber의 흐름으로 이해할 수 있고, `AnyPublisher`는 구체 구현을 호출자에게 노출하지 않는 경계가 된다.
- SwiftUI 레이아웃은 컨테이너가 공간을 제안하고 자식이 크기를 선택한 뒤 위치를 정한다. `@State`, `GeometryReader`와 `@ViewBuilder`는 각각 임시 상태, 제안 크기와 View 조합을 다룬다.

### SwiftUI 성능과 최신 프레임워크는 변경 범위와 기기 역량으로 판단한다

- SwiftUI 성능은 무엇이 바뀌고 어떤 View가 의존하는지 추적하는 변경 지역성의 문제다. 안정적인 identity, 좁은 binding과 render model로 불필요한 `body` 계산을 줄이고 `.task(id:)`의 취소와 오래된 결과 적용을 관리해야 한다.
- ScrollView의 target·position·transition API와 Swift Charts의 mark 조합은 상호작용과 데이터 표현을 선언적으로 구성하지만 Dynamic Type, VoiceOver, 대비와 지역화를 함께 검증해야 한다.
- SwiftData는 `@Model`, ModelContainer·ModelContext, `#Predicate`와 `@Query`로 저장과 UI 갱신을 연결한다.
- Metal 3, Vision과 Translation API는 렌더링·이미지 분석·번역을 기기에서 처리하는 범위를 넓힌다. 지원 family, 요청 revision, 언어 모델 상태와 실제 기기 제약을 먼저 확인해야 한다.

### 네트워크와 아키텍처는 경계와 단계로 설명한다

- 브라우저의 URL 해석부터 DNS 조회, socket 생성, 연결·송수신·종료까지의 단계를 분리하면 HTTP 요청이 실제 네트워크로 전달되는 흐름을 설명하기 쉽다.
- REST는 자원 중심 URI와 HTTP method뿐 아니라 status code, self-descriptive message와 HATEOAS까지 포함한 제약으로 이해해야 한다.
- DDD의 Bounded Context, Aggregate와 Repository는 모델의 적용 범위, 일관성 경계와 저장 책임을 분리한다.
- 슈퍼앱처럼 커지는 제품은 앱 구성, 비즈니스 로직과 UI 로직을 분리하고 Composition으로 기능을 조립해야 변경 범위를 통제할 수 있다.

### 심사 기록·릴리즈 노트·경력기술서는 독자가 다르다

- App Review 대응 이슈에는 Apple의 요청과 제출 체크리스트를, Release Notes에는 사용자가 체감하는 기능과 개인정보 보호 방식을 기록한다.
- 경력기술서는 업무 목록보다 문제와 해결 판단, 검증 가능한 결과와 실제 구현 범위가 이어져야 읽는 사람이 프로젝트의 인과관계를 이해할 수 있다.
- 공고에 중요하지만 최근 근거가 없는 BLE·GPS·보안 경험은 유사 경험으로 부풀리지 않고 보완 영역으로 관리하는 편이 신뢰를 높인다.
