# 2026-W48 · 11월 23일 ~ 29일

> 이 요약은 이번 주에 작성된 11월 23일·24일·25일·26일·27일 일일 TIL을 기준으로 한다. 11월 28일·29일 일일 기록은 아직 없다.

## 이번 주 한 줄

모바일 기능을 실제 환경과 자동화된 증거로 검증해 병합하고, 포트폴리오·면접·제품 문서·개발 하네스에서도 확인된 사실과 책임 경계를 기준으로 다음 실행 구조를 구체화했다.

## 완료한 일

### ReciteScripts 검증과 병합

- 스크린샷 후 낭독 유지, 홈 화면 전환 시 세션 종료, 정상 완주 안내 1회 표시를 실제 기기에서 검증하고 기기·OS·커밋과 결과를 Linear MAR-76에 남겼다.
- STT 준비 상태, 세션 생명주기, 접근성과 큰 글씨 레이아웃 변경을 정적으로 검토해 P0/P1 문제가 없음을 확인하고, 실행하지 못한 분석과 테스트는 미검증 범위로 분리했다.
- PR #135의 충돌, 정적 분석, 149개 테스트와 양 플랫폼 빌드를 확인한 뒤 병합했다.
- 읽은 위치 포인터, 한 어절 뒤로와 자동 스크롤 기준을 마지막으로 읽은 어절에 맞추고, 골든 테스트와 전체 157개 테스트, Android 실기기·iOS 시뮬레이터 통합 테스트를 통과한 PR #146을 병합했다.
- PR #145에서 수행하지 않은 STAB-02를 완료로 표현한 기록을 ‘미검증’으로 바로잡고 CI 통과 후 병합했다.

### 포트폴리오와 커리어 문서 정리

- 상품상세 재구축 포트폴리오를 2페이지 A4 HTML·PDF로 렌더링해 잘림과 겹침을 확인하고, 일정 판단·QA 범위·결과 수치의 측정 범위와 구현 한계를 보강할 지점을 찾았다.
- 포트폴리오 1·2에서 확정한 서사와 A4 작성 원칙을 재사용 가능한 스킬에 반영하고, 포트폴리오 3에서 원더픽의 MVP 출시와 베리모지의 Firebase 기반 운영을 별도 사례로 구분했다.
- 포트폴리오의 운영 기능을 측정·실험, 수익화, 리텐션으로 묶고, 확인되지 않은 수익·사용자·전환율·실험 결과를 성과로 쓰지 않는 기준을 세웠다.
- 잡코리아와 사람인의 경력 문서를 최신 자료로 갱신하고, 애즈위메이크 경력을 모듈화·상품상세 재구축·주문 관리·공통 개발 기반 중심으로 정리했다.
- 최신 제출물 6개를 면접 준비의 기준 원본으로 삼고 모듈화, 동시성, 이중 스크롤, 캐시와 App Extension을 우선 학습 영역으로 좁혔다.

### 개발 하네스와 공통 규칙 설계

- 하네스 엔지니어링 사례의 증거 인벤토리와 2페이지 포트폴리오 구조를 작성하고, 기간·PR·이슈·테스트 수치는 원자료 재검증 전까지 확정 성과에서 제외했다.
- 에이전틱 엔지니어링 10일 학습 계획에 공식 자료, 테스트와 Eval, 실패 징후, 단일 에이전트 기준선과 책임 점검을 배치했다.
- Anthropic의 에이전트 설계 자료를 Agentic Loop, 대표 워크플로, 검증과 도구 설계 원칙으로 정리했다.
- 개발 하네스에서 `verify`·`publish`·`cleanup` 단계를 분리하고, Hook 기반 외부 쓰기 차단, JSON Schema 계약·증거 검증과 재실행·정리 테스트를 강화하는 개선안을 도출했다.
- 공통 Developer 역할은 반복되는 위임·검증·PR 절차를, 프로젝트별 하네스는 모듈 관계와 객체 배치 같은 고유 결정을 소유하도록 경계를 정했다.

### 제품 설계와 외주 준비

- 단기 계획과 반복 루틴을 함께 관리하는 앱의 초기 사용자를 본인으로 정하고 별도 기획 워크트리를 시작했다.
- Manyfast는 요구사항, FigJam은 사용자 흐름, Figma Design은 화면의 기준 원본을 맡고 공통 기능 ID로 변경을 추적하는 제품 문서 구조를 정리했다.
- Penpot 전 화면을 복사하기보다 대표 화면을 Auto Layout, Component와 Variable 구조로 재구축해 전환 효율을 검증하는 단기 스프린트 방식을 선택했다.
- 초기 외주 서비스 3종의 범위, 제외 조건, 산출물, 기간, 상담·견적과 검수 기준을 정의해 Linear MAR-70을 완료했다.
- 프리랜서 준비 항목 MAR-75는 취업 준비와 충돌하지 않도록 2027년 1월 4일 시작으로 예약했다.

## 학습과 판단

### 완료는 구현이 아니라 증거의 범위로 판단한다

- 플랫폼 생명주기와 화면 상태는 정적 리뷰나 단위 테스트만으로 닫지 않고 실제 기기, 시뮬레이터, 골든 테스트와 통합 테스트를 조합해야 한다.
- 수행하지 않은 시나리오는 ‘미검증’으로 남겨야 PR과 릴리스의 실제 신뢰 범위를 보존할 수 있다.
- 테스트 통과, 실제 동작 확인, 이슈 기록과 병합은 서로 다른 완료 단계이며, 기기·OS·커밋과 시나리오별 결과를 남겨야 재현 가능한 증거가 된다.

### 문서의 설득력은 사실의 범위와 분류 기준에서 나온다

- 포트폴리오는 기능 수를 늘리기보다 문제, 제약, 대안, 결정, 검증과 한계를 연결하고 수치의 측정 조건과 관찰 범위를 밝혀야 한다.
- 광고·수익화·리텐션 기능은 구현 여부와 사업 성과를 구분해야 하며, 근거 없는 결과는 기반 구성이나 시도로 표현해야 한다.
- 경력과 지원 문서도 새로운 주장을 더하기 전에 최신 원문, 공개 범위, 서비스의 현재 상태와 시각 규칙의 일관성을 확인하는 것이 우선이다.

### 공통 규칙과 프로젝트 결정은 다른 주체가 소유한다

- 여러 저장소에 반복되는 위임, 검증, PR과 정리 절차는 공통 Developer 역할로 올릴 수 있다.
- 모듈 관계와 Client 배치처럼 프로젝트에서 이미 정한 구조는 일반 원칙으로 재해석하지 않고 프로젝트 하네스가 명시적으로 소유해야 한다.
- 구현, 검증, 발행과 정리를 분리하고 각 단계의 계약과 증거를 기계적으로 확인하면 외부 쓰기와 정리 실패를 독립적으로 통제할 수 있다.

### 제품의 기준 원본은 책임별로 나누고 ID로 연결한다

- 요구사항과 비즈니스 규칙, 사용자 흐름, 시각 상태를 서로 다른 도구에 맡기되 동일한 기능 ID를 사용하면 중복을 줄이면서 변경 추적성을 유지할 수 있다.
- 초기 사용자가 자신인 제품은 넓은 시장 가정보다 매일 사용할 최소 흐름과 반복 사용 여부를 먼저 검증하는 편이 빠르다.
- 디자인 도구 전환도 화면 복사보다 토큰, 컴포넌트와 반응형 제약을 다시 구성하는 작업으로 보고 작은 대표 화면에서 투자 효과를 확인해야 한다.

### 학습은 제출한 주장과 책임 범위에서 역산한다

- 면접 준비는 광범위한 지식을 순서대로 외우기보다 포트폴리오의 선택, 제외한 대안, 검증 결과와 한계에서 꼬리질문을 만들어야 한다.
- Agentic Loop와 도구 사용법뿐 아니라 단일 에이전트 기준선, 실패 징후, 결과를 AI 없이 설명할 수 있는지를 함께 점검해야 위임과 최종 책임의 경계를 유지할 수 있다.
- Swift 동시성, Testing, App Extension, App Intents, 구조화된 로깅과 아키텍처 패턴은 기능 자체보다 실행 제약, 상태 격리와 테스트 경계를 중심으로 학습해야 실제 경험과 연결된다.
